2. Updated: 2026-10-16
3. Related: P26; SUPPORT-001; UC-113 (Hra). See the [rules](../gap-analysis.md), [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).

7. Origin: [R-0018](done/R-0018.md). Explicit follow-up completed from the specification under the [migration](migration-2026-10-14.md).

## 1. Summary

1. The player needs to recover either the latest turn or the latest decade boundary without confusing them with the current Continue snapshot.

2. Migration observation (2026-10-14): The game already saves automatically at human-turn start and on the accepted menu path, but the catalogue identifies a single autosave destination rather than separate turn/decade recovery points.

3. Scope: the outcome and examples below. Selected and refined on 2026-10-16 under the remaining-backlog authorization; it does not reopen the delivered origin scope or close a whole UC.

## 2. Behavior

Acceptance refined on 2026-10-16; inherited resolved decisions remain agreed.

1. At the agreed turn and decade boundaries, preserve separately identifiable recovery saves with their actual game date.

2. Choose either recovery point → restore that point exactly, without replaying already processed turn effects.

3. The configured autosave-off choice prevents automatic writes. Existing manual save and Continue behavior remain available.

4. Failed writes retain the last valid recovery point and report failure; loading or inspecting one does not overwrite it.

5. Accepted behavior (2026-10-15; [recovery and presentation](../gap-analysis.md#recovery-and-presentation)): Offer distinct latest-position, latest-turn and previous-decade recovery, using the agreed human-turn checkpoint and ten-year boundary.

6. Shared update boundary (2026-10-15): apply this requirement within [national turn processing](../gap-analysis.md#national-turn-processing). Resume the saved completed boundary without repeating production, arrivals or action replenishment; future pending choices must preserve earlier completed updates.

7. Keep existing one-click Continue for Latest position and add an explicit recovery choice in the menu offering Latest position, Latest turn and Previous decade. Show each available file's actual in-game date and filesystem save time; missing slots are unavailable. Merely inspecting or canceling does not load, write or delete a slot. Malformed slots use R-0067 failure handling when selected.

8. Latest position remains the existing menu-exit snapshot. Fresh human-turn boundaries write Latest turn after automatic updates; crossing 1500, 1510 and subsequent decade boundaries writes Previous decade once, using the same snapshot. The initial 1490 start is not a decade boundary. Resuming a saved turn does not rewrite these points or repeat effects. Retain the last valid checkpoint until its own successful replacement, with truthful date labels even if another game was subsequently started.

9. Add a persisted autosave setting, enabled by default; disabling it suppresses automatic turn/decade writes, while manual Save and menu-exit Latest position still work. Write each save atomically using a sibling temporary file; a failed write keeps the previous destination bytes and reports failure. Failed menu-exit saving leaves the current game playable for retry. Do not silently fall back to destructive in-place writes. No eight-slot cap, migrations or cloud storage.

## 3. Implementation steps

1. Source inspection selects A04. `TurnStartedListener` already receives the safe fresh human-turn boundary; `Calendar.getYearForTurnNo` distinguishes the first crossed decade from later seasons. `PersistingTool` owns destination paths, `GameModelPoDao` owns serialized file writes, and `GameController`/`PersistingService` retain load/save navigation and feedback. Extend these owners without model-to-GUI dependencies.

2. First bounded implementation: shared atomic save replacement and separate checkpoint paths/coordinator with deterministic turn/decade policy and failure tests. Then wire the persisted setting, localized menu recovery choices/date labels and shared error feedback. Keep existing Continue/manual load and authored scenarios. Read metadata without starting a candidate or modifying files.

3. Model/service checks cover first turn, 1499→1500, seasonal decade boundaries, nonfresh resume, autosave off, independent file bytes and failed replacement. UI checks select both recovery points and compare exact model state after restoration, verify real dates, toggle autosave, preserve menu recovery/manual save, cancel without writes and retry after an invalid slot. Reuse stable TC42 rejection behavior and the [functional contract](../functional-tests.md).

4. Implementation and selected local acceptance are complete; full CI/publication remain pending. See [execution evidence](../functional-tests.md#r-0068-recovery-checkpoints-2026-10-16).

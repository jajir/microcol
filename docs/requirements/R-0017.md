# R-0017 — Use consistent command availability and rejection feedback

## 1. Summary

1. A player should understand why an action is unavailable and how to recover when a formerly valid action is rejected.

2. Z01 already uses a model preview, limited amount and revalidation. The architecture requires this pattern for shared model commands; it should guide consistent UI feedback.

3. Apply a shared presentation contract to two representative paths: cargo unloading and colony equipment changes. Do not create a new all-purpose command framework or rewrite every dialog.

## 2. Behavior

Proposed acceptance for individual refinement; capture does not approve implementation.

1. Unavailable actions show a meaningful reason, such as missing stock, capacity or ownership. UI reads model limits instead of maintaining duplicate rule formulas.

2. Confirmation presents the proposed quantity/cost and resulting action; Cancel changes neither model nor selection and returns focus to its invoker.

3. If state changes after preview, the model revalidates. Expected rejection refreshes the offer and explains what changed; no partial stock/equipment transfer remains.

4. Use consistent terms in Czech and English for the same resource/action. Feedback is understandable without sound or color and does not expose stack traces for expected rule rejection.

5. Keyboard and pointer paths invoke the same command. Unexpected programming errors remain diagnosable rather than being swallowed as ordinary validation feedback.

## 3. Implementation steps

1. Review existing Z01 controls and colony equipment callers; reuse their model operations and relevant GUI/i18n components.

2. Agree concise reason/confirmation patterns and apply them to the two paths, preserving existing behavior and IDs. Keep business validation in the model and translations in UI/i18n.

3. Proposed `TC_free_play_command_feedback_test` plus affected existing Z01/equipment scenarios cover unavailable, cancel, success and stale-state rejection. Verify unchanged stocks on failure and inspect text/focus visually.

## 4. Open questions

1. Use inline reasons next to disabled actions or a contextual help affordance? Blocking: yes for discoverability. Proposed answer: visible concise reasons for these dialogs, with no tooltip-only dependency. Decision: unresolved.

2. After stale-state rejection, keep the refreshed dialog open or return to its source? Blocking: yes for recovery. Proposed answer: keep it open if the subject still exists; otherwise return with an explanation. Decision: unresolved.

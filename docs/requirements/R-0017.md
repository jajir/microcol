# R-0017 — Use consistent command availability and rejection feedback

1. Status: Refining
2. Updated: 2026-10-13
3. Related: P28, P27; SUPPORT-004; UC-114 (Hra), UC-119 (Regrese). See the [rule catalogue](../gap-analysis.md),
   [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: Existing architecture transaction contract and UX guidelines; [R-0016](R-0016.md) screen context.
5. Primary area: [A03](areas.md#a03).
6. Related areas: A05/A06/A07 model validation; shared translated UI.

## 1. Summary

1. As a player moving goods or equipping a colonist, I want to understand which action I can take, what it will cost and what happened, so I can recover without losing my game state.

2. Existing Z01 unloading already offers a bounded amount and cancellation. Verify and reuse that player journey instead of prescribing a new command framework.

3. This analysis describes two representative use cases: unload goods and change equipment. Missing European equipment controls are tracked in R-0020.

## 2. Behavior

1. Use case 1 — unload goods: the player opens their colony, chooses their carrier and drags goods to storage. The game shows the amount that fits. Confirm transfers that amount and leaves the remainder aboard; Cancel leaves both inventories unchanged.

2. Use case 1 — no space: when storage is full, the player sees why nothing can be unloaded and can return to the colony without losing cargo.

3. Use case 2 — change equipment: the player selects their colonist, chooses available equipment, sees the required goods or gold and confirms. The same colonist receives that equipment; unrelated equipment and specialty remain.

4. Use case 2 — missing resources: the player sees what is missing and can cancel or obtain it. No stock or money disappears when the action cannot be completed.

5. Recovery — if the target or available resources change while a choice is open, the player gets a clear explanation and an updated choice. They can cancel safely. The game never applies part of the requested transfer.

6. The player can understand the outcome without sound or color alone. Mouse and available keyboard paths produce the same game result, with consistent Czech/English terms.

## 3. Implementation steps

1. Use the existing Z01 scenarios and the new equipment capability audit to identify which user steps already work and which are missing.

2. For each missing step, define one small change in the relevant requirement. Keep rule validation in the model and the player’s explanation in the screen.

3. Verify successful action, cancellation, unavailable resources and changed-state rejection through named UI scenarios before accepting the relevant implementation.

## 4. Open questions

1. Use existing visible error/quantity controls first. A universal new message layout is not a prerequisite; any remaining problem must be tied to a specific failed player step.

2. If a dialog’s subject disappears, return safely with an explanation. If only the available amount changes, refresh the choice. This is the proposed recovery detail to confirm against the concrete screen when implementing, not a blocker for the current audit.

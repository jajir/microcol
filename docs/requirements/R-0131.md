# R-0131 — Disband a selected empty unit safely

1. Status: new
2. Updated: 2026-10-20
3. Related: P06; MOVE-009; UC-016 (Hra). See the [movement rule](../gap-analysis.md#movement-and-persistent-orders), [accepted disband boundary](../gap-analysis.md#exploration-work-and-transport) and [use case](../use-cases.md#pohyb-a-rozkazy).
4. Dependencies: existing model unit deletion and carrier/passenger state from [R-0022](done/R-0022.md); order cancellation stays with each order's owner.
5. Primary area: [A05](areas.md#a05).
6. Related areas: A06 goods/passengers in carriers; A04 saved unit identity; A03 selection, confirmation and feedback.
7. Origin: MOVE-009 player-command gap in the [rule catalogue](../gap-analysis.md#movement-and-persistent-orders); preserve existing combat deletion behavior.

## 1. Summary

1. A player needs an explicit way to remove an owned unit permanently while keeping passengers, goods and saved selections safe.
2. The 2026-10-17 catalogue source assessment at `f902be8a` identifies a model deletion operation already used by combat, but no player disband command. This capture does not treat the deletion primitive as missing.
3. This requirement owns command eligibility, confirmation, removal and player-facing cleanup. It does not change combat destruction or replace cargo-transfer rules.

## 2. Behavior

1. The current player can select an owned eligible unit and choose Disband. The confirmation identifies the selected unit; accepting removes it from the world, active selection and saved game once. Cancel changes nothing.
2. A ship or wagon must be empty before disbanding. Passengers and goods must be unloaded first; a loaded carrier is refused with a usable reason and no change to carrier, passenger or goods state. Foreign or stale unit selection, invalid game phase and repeated confirmation reject without deleting another unit.
3. Any continuing order on the disbanded unit ceases with it, without performing its pending work or route step. Disband never advances the turn, settles a voyage or credits unfinished work. After Continue, the removed unit cannot reappear or remain selected.
4. This player command does not alter the separately delivered combat-destruction result or imply that every UC-016 cancellation variant has passed.

5. Agreed 2026-10-20 ([shared rule](../gap-analysis.md#r-0131-refinement)): On confirmed disbanding in an owned colony, return all actual equipment, including tools, horses and muskets, to that colony; outside an owned colony all equipment is lost. Confirmation shows exact quantities retained and lost. If warehouse capacity is exceeded, discard only the excess after explicit overflow confirmation; cancel changes nothing. Carrier cargo/passengers must still be unloaded first. Do not invent equipment.

## 3. Implementation steps

1. Add a model-validated player disband operation that checks live registered identity, current owner, phase and empty carrier state before using the existing deletion primitive. UI shows eligibility/confirmation and clears selection through existing controller behavior; AI uses the same model rule if it ever disbands.
2. Not prepared for development. On selection, return actual tools/horses/muskets through shared warehouse capacity rules. Validate the confirmed retained/lost quantities before any mutation and apply equipment transfer, confirmed excess loss and unit deletion atomically; stale capacity requires a refreshed confirmation. Preserve combat deletion semantics separately.
3. Proposed checks: owned ordinary unit, loaded/empty ship and wagon, wrong owner, stale/duplicate confirmation, order in progress, selection cleanup and disk Continue; include tools/horses/muskets inside/outside an owned colony, exact capacity, confirmed excess loss, cancellation and stale capacity without partial effects. Add a named UC-016 player scenario at refinement under the [functional contract](../functional-tests.md).

Refinement update 2026-10-20: implement the [accepted decision](../gap-analysis.md#r-0131-refinement) in the existing model owner and its UI/AI consumers; extend the named checks above for its boundaries, rejection, persistence and exactly-once effects.

## 1. Summary

1. The player can change or mute music and event effects separately and understand each control's current state.
2. Settings persist across restart without changing game state or depending on an audio device.

## 2. Behavior

1. Music and effect controls each have a visible range and an unambiguous silent state. Changes apply while running, survive restart and do not unexpectedly unmute the other category. Existing `soundEnabled=false` launch behavior remains an overall silent override for testing/headless use.
2. Missing audio hardware or unsupported gain leaves the settings view usable and saved preferences intact; muted play emits no cue but all text/visual outcomes remain. Cancel/reopen reflects the actual persisted choice.
3. Test category isolation, zero/silent boundary, restart and failure paths in model-free settings tests and actual supported-package listening.

## 3. Implementation steps

1. Selected after R-0228 in the authorized ordered batch. Reuse `Setting`, `SettingService`, `GamePreferences`, `PreferencesProperties` and the existing framed Settings view. Keep the existing music setting/API where useful; add only the effects preference and category-specific update path. Values are integers 0–100, each zero is silent. Show distinct localized Music/Effects captions, explicit silent endpoints and current values; use existing paper ruler controls and keyboard behavior, without a separate mute toggle that can contradict the slider.
2. Music keeps its existing saved value. For a preference file with no effects value, default effects to the existing valid volume, preserving a user's prior silence; a new installation uses the existing default volume for both. Validate/clamp malformed/out-of-range category values through existing preference ownership. These are application preferences, not saved-game data. Changes persist immediately as existing Settings do; Back/Escape/reopen and application restart retain both values independently.
3. Keep model/AI independent of audio. R-0228's `JavaSoundSuccessCuePlayer` reads the effects category and observes changes during playback; music uses only the music category. Ensure zero actually sends silence/stops audible output, including unsupported hardware gain. Fix only necessary music lifecycle/gain failure handling exposed by this contract: missing device, setting changes before line initialization and cleanup must not break Settings or game actions. Avoid a new generic audio engine. `soundEnabled=false` suppresses both categories regardless of saved values.
4. Reuse the current Settings layout in menu/game hosts. Preserve vertical-only overflow, fixed Back/title, normal fonts, readable localized labels and remaining preference order. Update all tests/page objects referring to the old single volume label/control. Keep stable scenario IDs; add named TC_84 settings scenarios for category independence, endpoints, keyboard operation, navigation/reopen and persisted values. Include relevant TC_192 host/size/language coverage and R-0228 victory/failure paths; keep assertions only in page `verify...` methods with existing fixtures and linear English TC steps.
5. Add focused preference/model-free audio tests for independent persistence/restart, defaults for existing values, range/silent boundary, global override, live changes and missing/unsupported audio device. Preserve and extend R-0228 output-byte tests; do not rely solely on mocked setter calls to claim silence.

# R-0227 — Control music and effect volume independently

1. Status: new
2. Updated: 2026-10-17
3. Related: P30/P28; [volume and mute behavior](../audio.md#hlasitost-a-vypnuti-zvuku), [shared UX rules](../ux.md#spolecna-pravidla-pro-dalsi-zmeny).
4. Dependencies: existing user preference storage and music control; event effect service [R-0226](canceled/R-0226.md). No saved-game schema compatibility migration is required during development.
5. Primary area: [A03](areas.md#a03).
6. Related areas: A01 settings, A04 preference persistence.
7. Origin: remaining P30 player control once event effects are introduced; existing single music-volume control is credited.

## 1. Summary

1. The player can change or mute music and event effects separately and understand each control's current state.
2. Settings persist across restart without changing game state or depending on an audio device.

## 2. Behavior

1. Music and effect controls each have a visible range and an unambiguous silent state. Changes apply while running, survive restart and do not unexpectedly unmute the other category. Existing `soundEnabled=false` launch behavior remains an overall silent override for testing/headless use.
2. Missing audio hardware or unsupported gain leaves the settings view usable and saved preferences intact; muted play emits no cue but all text/visual outcomes remain. Cancel/reopen reflects the actual persisted choice.
3. Test category isolation, zero/silent boundary, restart and failure paths in model-free settings tests and actual supported-package listening.

## 3. Implementation steps

1. Extend existing preference/view/audio ownership rather than saving audio settings inside a game snapshot. Apply the same category values in R-0226's service, with listener cleanup and no model dependency.
2. Current result: captured setting outcome only. The dated [audio source audit](../audio.md#hlasitost-a-vypnuti-zvuku) describes a historical single-slider state, not verified current playback.

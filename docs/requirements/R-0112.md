# R-0112 — Stabilize TC27 and TC30 map interactions

1. Status: ready for development
2. Updated: 2026-10-15
3. Related: P31; regression protection for existing UC-018/024/027/055/057/113/114 paths in the [use-case catalogue](../use-cases.md). No new gameplay outcome is claimed.
4. Dependencies: existing [Docker runner](done/R-0033.md), Linux CI and [functional test contract](../functional-tests.md).
5. Primary area: [A03](areas.md#a03), shared UI interaction and feedback.
6. Related areas: A05 map movement; A06 equipment, transport and specialist purchase; A04 current-turn ownership and saved-game continuation. Preserve these existing outcomes.
7. Origin: user request on 2026-10-15 to capture the TC27/TC30 instability and proposed resolution after the 2026-10-14 analysis; not part of the backlog migration.

## 1. Summary

1. Developers need repeatable UI regression results and enough failure evidence
   to avoid spending development time on speculative changes to working gameplay.
2. Existing CI alternates between success and an empty map status-bar assertion
   in TC27/07 or TC30/04. Relevant game/test and runner sources were identical
   across successful and failing revisions. The [dated evidence](../functional-tests.md#tc27tc30-stability-analysis-2026-10-15)
   establishes the symptom, not its cause or a measured random-failure rate.
3. Scope: diagnose and correct the causes of these two journeys' unstable map
   interactions, including shared helpers and any application defect actually
   reproduced. Do not replace the test framework or change voyage, equipment,
   purchase or production rules to obtain a pass. The separate production
   discrepancy remains owned by [R-0061](R-0061.md).

## 2. Behavior

Refined on 2026-10-15 after the native full-class failure; existing gameplay expectations remain binding.

1. With fixed sources, fixtures and a recorded runtime, the developer runs the
   existing TC27/07 equipment/transport/Continue and TC30/04 specialist/transport/
   workplace journeys. Their real UI actions and original assertions complete
   consistently in the agreed repetition campaign, both individually and with
   surrounding scenarios in local Docker and Linux CI.
2. A failed action remains a failure and identifies its phase and observed state.
   Evidence distinguishes missing/delayed input, unfinished movement or rendering,
   and an incorrect result after delivered input; an unresolved cause stays open.
3. Preserve rejection, cancellation, identity, cargo, funds, equipment, workplace
   and save/Continue checks. A genuinely missing result still fails within a
   bounded wait. Do not suppress assertions, skip scenarios, bypass UI actions
   through model mutation, or hide a failure behind an automatic retry.
4. Every measurement records the first result, selection, source/image identity,
   duration and failure evidence. Repeating a failed run is diagnostic evidence,
   not erasure of the failure. One green run does not establish stability;
   completion requires the agreed campaign and full mandatory regression with
   no failures, errors or skips in the acceptance runs.
5. After the model hands control back to the human player, a delayed notification
   about the previous computer turn cannot disable map hover or colony selection.
   Map input remains unavailable without a running game or during a computer turn;
   the existing animation guard remains effective.

## 3. Implementation steps

1. The [native diagnostic evidence](../functional-tests.md#r-0112-diagnostic-campaign-2026-10-15)
   captures TC27/07 failing after correctly delivered map movement while input
   remains disabled after the human turn started. `ListenerManager` dispatches
   turn notifications concurrently; `GamePanelController` caches the event's
   player and can retain a late computer turn. The earlier missing-movement
   hypothesis does not explain this trace and is not the selected repair.
2. Remove the redundant cached turn owner from `GamePanelController`; use the
   existing `GameModelController` and current live model when deciding whether
   input is allowed. Publish `GameManager.currentPlayer` and the controller's
   movement flag safely across model/FX threads. Preserve animation handling,
   mouse gestures and model rule validation; no event-dispatch redesign.
3. Add `GamePanelControllerTest` for live ownership, delayed notifications,
   unloaded/stopped games and retained movement handling. Reproduce delayed
   computer notification in `TC_21_F15_free_play_screen_navigation_test#TC_09_late_computer_turn_notification_does_not_block_the_current_human`:
   load the human turn, deliver the old UI notification, hover the colony and
   open it with native input. Keep assertions in page `verify...` methods.
   Demonstrate failure with the old cached gate before accepting the fix.
4. Initial diagnostics were bounded at three fresh runs per selection/environment
   and stopped on failure. The failure appeared with surrounding class scenarios,
   so acceptance now repeats both **complete TC27 and TC30 classes ten times per
   environment**, each class in its own JVM and each repetition in a fresh
   container. Budget 45 minutes per campaign, stop on any failure. Keep native
   Linux and local amd64 emulation separate, retain every first result and source/
   image/fixture identity. Remove temporary verbose tracing after diagnosis;
   retain concise failed-action state and the manual repetition workflow. Apply
   the [shared Java formatter](../code-formatting.md).
5. Verify the unchanged named methods
   `TC_27_F19_europe_equipment_test#TC_07_equipment_and_identity_survive_embarkation_voyage_and_continue`
   and `TC_30_F22_expert_purchase_test#TC_04_hired_expert_sails_home_and_works_in_the_smithy`,
   then the complete-class campaign, the new delayed-notification scenario,
   affected shared-helper callers and `PageVerificationContractTest`. Repeat the agreed campaign after the fix and
   run the full Docker/CI regression. If map feedback changes, retain TC21/08 and
   `MouseOverTileManagerTest`. Record actual results in the linked evidence page
   and independently verify publication under the normal completion workflow.
6. Current result: the live-owner gate and deterministic regression are implemented.
   [Targeted checks passed](../functional-tests.md#r-0112-map-input-repair-2026-10-15);
   repeated full-class acceptance, full regression and publication are pending.
   Existing failures remain evidence.

## 4. Open questions

1. Question: which event/state transition causes each empty status result, and
   do both journeys share one cause? Blocking: no.
   Decision (2026-10-15): TC27's captured failure is a disabled application input
   gate after delivered movement. Both journeys share that gate. Repair its
   stale turn cache and verify both journeys; earlier TC30 failures lack this
   trace, so do not claim every historical failure had the same cause.
2. Question: what repetition counts and acceptance threshold provide useful
   evidence within the agreed local/CI time budget?
   Decision (2026-10-15): the bounded campaign in 3.4 is selected for this work.
   Blocking: no. Require zero failures/errors/skips; report the observed sample
   without claiming that a finite run proves absence of all intermittent failures.

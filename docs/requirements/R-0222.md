# R-0222 — Audit shared game controls for access and recovery

1. Status: new
2. Updated: 2026-10-18
3. Related: P28; [shared UX rules](../ux.md#spolecna-pravidla-pro-dalsi-zmeny), [UC-119](../use-cases.md#souvisle-pruchody-beznou-hrou) (**Regrese**).
4. Dependencies: delivered navigation [R-0016](done/R-0016.md) and command rejection [R-0017](done/R-0017.md); report/help surfaces [R-0198](R-0198.md)–[R-0207](R-0207.md); connected journeys [R-0217](R-0217.md)–[R-0220](R-0220.md).
5. Primary area: [A03](areas.md#a03).
6. Related areas: A01 menu, A02 setup, A04 save/recovery; individual feature owners retain their commands.
7. Origin: shared residual accessibility/interaction acceptance, not a replacement for UX checks in each feature R.

## 1. Summary

1. Across ordinary game screens, players can recognize state, find expected actions, recover from a canceled or rejected action, and operate essential paths without relying only on a gesture, color or sound.
2. This requirement owns a cross-screen audit and bounded shared-control repairs discovered by it, not a full redesign or new game rules.

## 2. Behavior

1. In New Game, map, colony, Europe, reports and end views, selection/focus, current turn, action availability, price/consequence preview and actual result remain understandable at relevant window sizes and with supported text lengths. Expected but unavailable actions expose a reachable reason; canceled actions preserve prior state.
2. Essential actions have a discoverable mouse path and workable keyboard focus/navigation. Important states and outcomes remain distinguishable without audio or color alone; localization length does not hide confirmation or cancel controls. Apply the [accepted hand-drawn control and stroke rules](../graphics.md#minimalisticky-graficky-manual), including readable focus at final UI size.
3. Record each screen/control variant, input method, expected result and actual evidence. Repair a shared component here only when the defect is genuinely shared; route feature-specific behavior failures to their owning R. Passing automated UI paths alone does not prove a player can discover them.

## 3. Implementation steps

1. Build a cross-screen checklist from the [UX rules](../ux.md) and [final-size visual checks](../graphics.md#export-a-kontrola-vysledne-velikosti), then inspect actual rendered states and run affected named `TC_...` paths under the [functional contract](../functional-tests.md). Keep assertions on game behavior while repairing shared focus, labels or layout.
2. Current result: captured audit scope only. The 2026-10-11 UX source observations and current feature tests are not a completed whole-game accessibility audit.

## 4. Open questions

1. None. Keyboard, mouse, readable focus and non-color/non-audio meaning are the baseline here; any wider assistive-technology certification needs separate selection.

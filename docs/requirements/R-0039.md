# R-0039 — Prefer local work and preserve budgets when escalating to high

1. Status: Verified; publication checked separately for the resulting commit
2. Updated: 2026-10-14
3. Related: [R-0038](R-0038.md), [P31](../implementation-plan.md#seznam-pracovnich-baliku), [worker operations](../ai/local-qwen.md).
4. Primary area: [A03](areas.md#a03), shared development and verification support.
5. Cross-area dependencies: none; no gameplay, Java package or saved-data change.

## 1. Summary

1. The user prioritizes saving cloud tokens over speed and unnecessary parallel
   cloud work, and authorizes medium/64k followed by high/64k when justified.
2. The previous default was medium/16k; the launcher rejected every profile change
   during a task. High/64k is already installed and has dated trial evidence.
3. Keep the main agent responsible for requirements, review and actual checks.
   Apply this policy to the current task without extra cloud agents.

## 2. Behavior

1. Project instructions prioritize cloud-token economy. Delegate suitable bounded
   work locally; avoid duplicate cloud implementation/review and broad repeated
   discovery. Required validation and acceptance remain mandatory.
2. New ordinary jobs use medium, context 98304 and generation allowance 65536,
   with 7200 seconds per attempt, 14400 seconds total and at most two repairs.
3. After diagnosing failure, fix caller setup or unclear requirements first and
   target simple repairs. Escalate to high when medium still cannot solve the
   task or exhausts generation, before consuming the remaining repair budget.
4. The caller explicitly records the escalation reason. The launcher permits
   only medium to high with every other profile field unchanged, in the same
   job/worktree and with the same installed digest. No automatic blind retry,
   downgrade, time reset or repair-count reset is allowed.
5. Historical jobs retain their original profiles. Configuration checks and
   launcher tests do not establish medium/64k coding reliability or measured
   cloud-token savings.

## 3. Implementation steps

1. Update AGENTS.md and the existing worker skill/operating page. Reuse the
   installed 96k-context / 64k-output alias for the default medium profile.
2. Extend the existing budget/run path with a diagnosed escalation argument;
   preserve immutable attempt profiles and record the transition reason.
3. Verify allowed transition, subsequent high repair, refused changes/downgrade,
   missing reason and preserved time/repair limits in launcher tests. Verify the
   installed alias and effective command settings without a new long benchmark.
4. Run documentation tests, strict MkDocs, review the diff and rendered links,
   then commit/push main and verify Pages and development publication.
5. Evidence on 2026-10-14: all 21 launcher tests and nine documentation tests
   passed, as did the strict MkDocs build. The installed alias matches both
   profiles (98304 context, 65536 generation, medium/high capability); command
   construction selects medium by default and disables worker delegation.
   No new model download or inference was needed. Profile evidence is retained
   in `target/r39/profile-verification.json`; dated coding results remain in
   R-0036/R-0038. This task used no additional cloud agents.

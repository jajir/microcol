## 1. Summary

1. The player needs changing a construction project to preserve the agreed usable work, without duplicating progress across queued entries.

2. Migration observation (2026-10-14): R-0025 preserves progress per queue entry and explicitly leaves a new hammer-retention policy outside its scope. The manual describes retained hammers when changing project.

3. Scope: the outcome and examples below. Selected and refined on 2026-10-16 as the shared-pool prerequisite of R-0083; it does not reopen the delivered origin scope or close a whole UC.

## 2. Behavior

Agreed acceptance refined on 2026-10-16.

1. Accumulate hammers on project A, switch to B → retain and credit exactly the agreed amount to B.

2. Switch back or reorder repeatedly → never duplicate the same hammers or erase them without the agreed explicit consequence.

3. Cancel a queue edit → retain order, identities, progress and stocks; tools are consumed only by the existing valid completion operation.

4. Save/load preserves transferred progress and mixed unit/building order. Reuse accepted population-start and predecessor-completion gates.

5. Accepted behavior (2026-10-15; [economy, production and education](../gap-analysis.md#economy-production-and-education)): Retain one colony hammer pool through head changes/removal/reordering; consume only completed costs and carry surplus forward.

## 3. Implementation steps

1. Use the existing colony warehouse HAMMERS balance as the single pool. Remove item-owned hammer state from runtime and current-schema queue entries; preserve item IDs/order/type. Update bundled fixtures directly, with no save migration. The displayed current project uses the pool; queued projects do not each claim the same progress.

2. Reuse existing completion gates. If either hammers or tools are insufficient, retain both stocks and queue. On success consume exact costs, preserve surplus, complete only the head once per update and leave remaining entries untouched. Empty queues retain production. Population remains a start-only gate.

3. Model cases cover A→B→A, removal, empty queue, mixed building/unit order, missing tools, surplus sufficient for multiple projects but only one completion, failed prerequisites and save/load. `TC_54_F45_shared_hammers_test` exercises actual queue changes and Continue, and TC32 expectations follow the shared pool without weakening admission/cancel assertions. Follow the [functional contract](../functional-tests.md).

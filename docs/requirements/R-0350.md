# R-0350 — World minimap in the right sidebar

1. Status: new
2. Updated: 2026-10-30
3. Related: [UC-114/119 and the UI catalogue](../use-cases.md), [visual brief](../graphics.md#soucasne-zadani-vzhledu), [UX guidelines](../ux.md).
4. Dependencies: existing map navigation and [R-0070 explored terrain and current visibility](done/R-0070.md).
5. Primary area: [A03](areas.md#a03).
6. Related areas: [A05](areas.md#a05), for the player's permitted knowledge of the world.
7. Origin: user request on 2026-10-30 for seven visual proposals based on an attached main-game screenshot; gameplay implementation has not been requested.

## 1. Summary

1. Give the player a world overview and a direct way to move the detailed map to a chosen location.
2. The supplied screenshot has player and terrain information at the top of the right sidebar and no minimap. It is the visual reference, not evidence of the current executable revision.
3. Capture the requested behavior and prepare visual alternatives. The [first gallery](../graphics.md#minimapa-sedm-navrhu-30-rijna-2026) contains seven styles; the follow-up request on 2026-10-30 adds [seven more reduced scales](../graphics.md#minimapa-sedm-meritek-30-rijna-2026). Neither a final style nor scale has been selected.

## 2. Behavior

1. The minimap sits at the top of the right sidebar, above the existing player and terrain information. It always represents the full playable world's extent, with terrain indicated by color and land boundaries by strong hand-drawn lines.
2. Clicking a location on the minimap moves the detailed map to that location. A closed rectangle shows which part of the world the detailed map currently displays and follows changes to that view.
3. Unexplored areas remain concealed. The world outline describes the playable bounds; it does not reveal unknown coastlines, terrain or objects. Rendering follows the player's existing knowledge rules in R-0070.
4. Proposed boundary behavior for refinement: clamp the detailed view at world edges, preserve the world's aspect ratio, and make navigation change only the view, without issuing a unit order or discovering terrain. Existing information below the minimap must remain usable in small windows.

## 3. Implementation steps

1. No gameplay implementation in this task. After selection for development, inspect the existing map view and navigation owner in `gui.screen.game` and reuse model visibility queries under the [architecture contract](../architecture.md#prozkoumany-teren-a-soucasny-dohled-r-0070).
2. Refine sizing, coordinate conversion, map-edge behavior, keyboard access and updates after scrolling, window resize and discovery. Keep runtime assets, Java, fixtures and UI scenarios out of this design-only change.
3. Design acceptance: inspect all delivered previews, verify relative links, run documentation consistency tests and the strict MkDocs build. Future gameplay acceptance requires named map-navigation and visibility scenarios, model/JUnit, targeted Docker/Xvfb and smoke according to the [local policy](../publishing.md#local-acceptance-policy); those scenario assignments remain to be prepared at refinement.
4. Current result: seven style proposals and seven further scale proposals, without an interactive game feature or verified world-coordinate mapping. The [scale series](../graphics.md#minimapa-sedm-meritek-30-rijna-2026) targets approximate world-to-view width ratios of 3, 4, 5, 6, 8, 10 and 12; geography outside the supplied view is illustrative. These are design comparisons, not exact coordinate specifications or new world-size settings. Actual full-world scale must derive from world and minimap dimensions.

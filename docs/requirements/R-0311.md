# R-0311 — Runtime developer mode and map coordinates

1. Status: new
2. Updated: 2026-10-27
3. Related: UC-006 (map information), UC-114 (controls), UC-119 (Regrese), [UC catalogue](../use-cases.md); P27–P30 in the [implementation plan](../implementation-plan.md).
4. Dependencies: existing Settings persistence, map-hover descriptions and model visibility queries; no map editor prerequisite.
5. Primary area: [A03](areas.md#a03), screens and shared UI language.
6. Related areas: A01 owns Settings entry/return; A05 supplies map coordinates and visibility. Neither game rules nor map data change.
7. Origin: on 2026-10-27 the user proposed developer settings, hover coordinates for future map editing, and a shortcut for comparing normal/developer views; requested advice and a shortcut proposal.

## 1. Summary

1. Let a developer or map author switch additional diagnostic information on and off during the same game, without restarting or changing the position being inspected.
2. Source inspection on 2026-10-27 at `d7308d49149eea9ab476966dee6968090a32f907` found an existing hover description in the status bar. Coordinates already appear when the launch property `development` is true. Settings has no runtime developer switch. This is source evidence, not a player test.
3. Capture the requested capability and the recommendations below. The first proposed delivery contains one switch, one shortcut, a visible mode indicator and hover coordinates. Additional menu actions need concrete follow-up requirements; a map editor, cheats and a general diagnostic console are outside this first outcome. Runtime implementation has not been selected.

## 2. Behavior

1. **Proposed discovery:** Settings, accessible from the main menu and during play, gains a small “Vývojář / Developer” section with “Režim vývojáře / Developer mode”, its F3 shortcut and a short explanation. Reuse the existing checkbox presentation; a separate settings screen is unnecessary for one option.
2. **Proposed state:** default off for a new preference profile. Remember the choice with application settings, independently of saved games. The checkbox and shortcut always change the same state, immediately and without confirmation or restart. Returning from Settings or loading another game preserves this preference.
3. **Proposed shortcut:** F3 toggles the mode in the main game screen and Settings, including while waiting for the AI. One physical press toggles once; holding it must not repeatedly toggle. It does not issue a unit command, advance a turn or dismiss a dialog. Modal dialogs and text entry retain their normal input handling. Display the new state briefly and keep a small “DEV” indicator visible while enabled, without replacing the hovered tile description.
4. **Proposed hover:** normal mode keeps the ordinary tile description; developer mode adds a clearly labelled coordinate pair, for example “x=12, y=8 · Les”. Toggling with a stationary pointer immediately refreshes the current tile. Moving outside the map clears its coordinates. Both modes preserve existing information about terrain and known objects; the switch reveals no hidden terrain, units or settlement information.
5. **Coordinate contract:** use the existing map-file/model convention: the top-left valid tile is `[1, 1]`, x increases to the right and y downward. Show coordinates on valid unknown tiles too, together with the ordinary unknown-tile description. Scrolling must not change the coordinates of the same tile. A future map editor should use the same convention.
6. **Shortcut rationale:** F3 has no binding in the inspected game sources and is an established diagnostic-screen example in [Minecraft Java Edition](https://www.minecraft.net/en-us/article/exploring-minecraft). On an Apple keyboard it may require Fn+F3, depending on function-key settings ([Apple guidance](https://support.apple.com/en-ie/102439)). The Settings control remains the discoverable alternative; actual platform behavior still needs testing.

## 3. Implementation steps

1. After selection, refine a runtime preference through existing `gui.preferences` owners (`Setting`, its copy/equality handling, `SettingService`, `GamePreferences`) and `gui.screen.setting`. Keep diagnostics in GUI; reuse model coordinates and visibility without adding GUI dependencies to model or AI. Follow the [package map](../architecture.md) and [UX guidelines](../ux.md).
2. Reuse `StatusBarMessageService`, `MouseOverTileManager` and `MouseOverTileListener` for formatting and immediate refresh. Route Settings and keyboard actions through the same preference update. Update EN/CZ resources, the mode indicator and relevant page objects. Do not introduce an extension registry for unspecified future tools.
3. Keep the runtime preference distinct from the existing launch flag. The three inspected `isDevelopment()` consumers are `MicroColApplication` (CSSFX startup), `SecretOption` (hidden menu behavior) and `StatusBarMessageService` (coordinates). The proposed checkbox owns displayed diagnostics; it must not start CSSFX or implicitly expose hidden actions. Preserve the launch flag's other uses and check launch/test configuration when moving the coordinate condition.
4. Verification plan: extend `StatusBarMessageServiceTest` for both states and unknown tiles; test preference default/copy/persistence. Extend `TC_84_F75_framed_settings_test` with Settings/keyboard synchronization, stationary-pointer refresh, held-key behavior, mode indicator, valid map corners, scrolling, hidden information, text/modal input and persistence across restart/load. Reuse existing map scenarios where appropriate and preserve the [functional-test contract](../functional-tests.md). Apply the shared [Java formatter](../code-formatting.md), then run model/JUnit, targeted Docker/Xvfb scenarios and fixed smoke acceptance for implementation; documentation checks remain required.
5. Current result: proposal captured only. No runtime, assets, tests, map fixtures or configuration changed. Documentation acceptance is recorded in [publishing evidence](../publishing.md#r-0311-developer-mode-proposal-2026-10-27); it does not verify the proposed feature.

2. Updated: 2026-10-15

5. Primary area: [A05](areas.md#a05).
6. Related areas: A03 command/keyboard discovery; A04 owner-turn restoration and saved movement.
7. Origin: [R-0003](canceled/R-0003.md), retained under the [migration](migration-2026-10-14.md).

## 1. Summary

1. The player needs distinct, discoverable choices to postpone a unit within this turn or finish its actions for this turn.
2. Selected and refined on 2026-10-15 under the authorized implementation run. Source inspection confirms Tab cycles owned on-map units with movement and wraps. There is no separate player Skip turn command. Existing zero movement already persists and replenishes on the owner's next turn.
3. Scope: expose Wait, add Skip turn, and verify zero/one/many-unit behavior and Continue. Persistent sentry, fortification and other standing orders remain outside this requirement.

## 2. Behavior

Agreed behavior reuses the existing wait-like cycling; control and edge choices were resolved on 2026-10-15 under the user's authorization to choose reasonable defaults.

1. The game toolbar shows labeled Wait (Tab) and Skip turn (Space) controls. Their tooltips explain whether movement is preserved or spent. Labels and feedback are available in English and Czech. No sound is required to understand either result.
2. Wait selects the next eligible unit without spending movement or changing its order. Normal cycling includes only the current player's registered on-map units with remaining movement and no continuing work; it wraps in the existing stable order. With three units, repeated Wait returns to the first after the other two. With one, it stays selected. With none, selection becomes empty and commands remain unavailable; no loop or enemy selection occurs.
3. Skip turn spends all remaining movement of the selected eligible unit and selects the next available unit. If none remains, selection clears. It never advances the calendar or ends the player's turn automatically. A later manual selection may inspect the spent unit, but cannot move or skip it again this turn.
4. Skip creates no persistent order and does not change location, cargo, passengers, equipment, stocks or gold. Saving and repeated Continue preserve spent movement; the next ordinary owner turn restores normal movement. Waiting requires no saved order because it changes selection only.
5. Commands are unavailable during preparation, a rival turn, stopped/finished games or a movement animation. An enemy, removed/replaced unit, off-map unit, spent unit or unit performing continuing work cannot be skipped. The model rejects stale/invalid requests before mutation; UI refreshes availability and explains a rejected action. Empty selection is harmless.
6. Wait or Skip cancels an unconfirmed movement preview when selection changes; it does not execute that path. Actions apply immediately, without a confirmation dialog. Before choosing them the player can simply keep the current selection or cancel the movement preview with Escape. Existing Tab cycling remains available and Space must invoke Skip once, even when a toolbar control has keyboard focus.

## 3. Implementation steps

1. Model owns `canSkipUnitTurn(Unit)` and `skipUnitTurn(Unit)`. The query checks a running, fully prepared game, identical registered current owner/unit, map placement, positive movement and no ongoing action. Revalidate in the command before using the existing no-action operation that spends movement and emits action feedback. Preserve `availableMoves` persistence and normal owner-turn activation; add no schema flag or migration.
2. Reuse `UnitStorage`'s stable next/first selection and exclude continuing work from normal activation. Keep manual tile inspection's fallback to spent units. UI and AI may use the shared model command; do not add model-to-GUI dependencies.
3. Keep unit selection in `SelectedUnitManager`, handling the existing SelectNextUnit event and the new Skip event with shared readiness checks. Clear selection when normal cycling is empty. Reuse the existing move-mode and refresh events; selection changes cancel an unconfirmed path. Toolbar controls use model availability, labels/tooltips and the existing language update path. Handle Tab/Space before focused controls can consume them or trigger a second action; preserve other keyboard commands.
4. Use the configured local worker for bounded model/query/test work. Main owns the refined interfaces, UI integration, review and actual acceptance. Use the shared Java formatter and profile; no Maven while the local model is loaded. Retain exact source anchors and repair evidence under the documented worker workflow.
5. Add `UnitTurnOrdersTest` for cycling, one/zero units, skip atomicity and save/resume/restoration, unavailable states and stale identity. Extend `TC_11_F11_skip_to_next_unit_test` with stable new scenarios for buttons/keys, multiple/one/zero units, selected-unit state, Continue, next turn, preview cancellation and blocked input. Keep the existing scenario ID and fixture; use page-object verification methods and current-schema data.
6. Run model boundaries, `UnitStorageTest`, `TurnPreparationActionTest`, `NationalTurnPreparationTest`, `PageVerificationContractTest`, TC11 and affected navigation/movement/TC36 journeys in Docker/Xvfb/Openbox. Inspect actual UI layout at the supported test size, retain gameplay assertions, then run full regression and publication gates. Record results in [functional evidence](../functional-tests.md), update the rule/UC and package responsibility descriptions, and only then mark done.

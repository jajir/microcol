# R-0432 — Readable save filenames

## 1. Summary

1. Players need short, recognizable filenames when inspecting or copying their saved games outside the game. Requested examples are `autosave-001.akropia` through `autosave-005.akropia` and `duch-1600.akropia`; an explicitly entered save name must be reflected in the filename.
2. Source inspection at `f29bf15e` on 2026-11-08: `SavedGames` creates `saves/<playthrough UUID>/`; manual targets use a new UUID, quick save uses `quick.akropia`, and turn snapshots use `turn-` plus a ten-digit increasing write sequence. Five snapshots are already retained per playthrough. These UUIDs identify games/files; they are not content hashes. The screenshot is consistent with this structure, but does not identify which games the two directories contain.
3. `GameModelDao` already stores a readable name in archive metadata: the supplied name, or player name plus game year/season. `PersistingService` chooses the random manual target separately, so the display name does not determine the filename. Independent root recovery slots explain `latest-turn.akropia` and `previous-decade.akropia`; they are outside the five-file history.
4. Scope is naming and its safe integration with existing save management. No gameplay implementation or modification of the user's existing saves is authorized by this analysis. Directory naming remains an explicit design question.

## 2. Behavior

1. Requested: retain the latest five successful automatic turn saves with short `autosave-NNN.akropia` names, independently for each playthrough. Preserve existing save timing, failure reporting, manual/quick-save independence and read-only loading under the linked save policy.
2. Proposed for decision: `autosave-001.akropia` always denotes the newest successful snapshot and `autosave-005.akropia` the oldest. With fewer than five saves, use only the needed names. Loading an earlier turn does not rotate them; the next successful new-turn save becomes 001 regardless of game year. An alternative is five reusable circular slots, whose numeric names do not imply age.
3. Requested: manual saves use a readable default such as `duch-1600.akropia`; user input such as `Před útokem` produces `Před útokem.akropia`. Proposed default source is the existing player name plus date, retaining season where relevant; a separate new game-title field is not assumed.
4. Proposed: retain Unicode letters, accents, punctuation and internal spaces wherever portable filesystem rules permit them, with existing Unicode trimming and 64-code-point input validation. Reject path separators, traversal and unsupported filename characters with clear feedback rather than silently changing the supplied name. Handle an already supplied `.akropia` suffix once. Reserve managed quick/autosave names so manual saves cannot enter automatic cleanup.
5. Proposed: a new save whose filename already exists receives a short suffix, for example `duch-1600-2.akropia`; only the existing explicit overwrite action with confirmation may replace a manual save. Include case-insensitive and Unicode-normalized collisions. Cancellation leaves files and the active game unchanged.
6. Preserve complete recovery states on write failure or interruption. Continue and the save browser must still identify the intended state after any renaming. Merely listing or loading an archive must never rename, rewrite or rotate it. Existing files are not silently migrated or deleted.

## 3. Implementation steps

1. Resolve chapter 4 before marking ready or implementing. The authoritative current behavior remains the [save policy](../save-load-navigation.md); this file distinguishes requested naming from proposed decisions.
2. Keep persistence ownership in `model.campaign.po.SavedGames` and `GameModelDao`, with UI actions and feedback in `gui.dialog.PersistingService` and the saved-game browser, following the [package map](../architecture.md). Reuse archive metadata and atomic writing; UUID identity can remain inside archives even if paths become readable.
3. A filename-only substitution is insufficient: current history ordering and cleanup parse monotonically increasing filenames. Define durable successful-write ordering and crash recovery before choosing rank-based rotation or circular slots. Review Continue's persisted path, overwrite/delete, imports/exports, managed-kind recognition and recovery files together. Rank rotation must not let a stale path select a different snapshot or let interruption destroy previous saves.
4. Extend service/model checks for 0/1/5/6 saves, restart, replay, separate games, Unicode, forbidden names, reserved names, collisions and failed/interrupted writes. Extend `TC_43_F34_recovery_points_test`, `TC_42_F34_load_recovery_test` and `TC_191_F224_session_menu_test` for history, Continue and manual/quick save behavior. Preserve existing assertions and stable scenario IDs; select additional saved-game browser scenarios during implementation refinement.
5. Future executable acceptance requires formatter review where applicable, all model/JUnit checks, targeted Docker UI scenarios, fixed smoke selection and documentation checks. This analysis has only source-inspection evidence; it does not establish runtime acceptance of the proposed naming.

## 4. Open questions

1. Should 001 always mean newest (recommended for browsing), or should 001–005 be circular slots whose age is determined by metadata?
2. Does `duch` mean the player's existing name, or a separate title for the whole game? Proposed default reuses player name and game date; custom save names remain available.
3. Should playthrough directories retain UUID names, or also become readable? Recommended usability option is a stable readable directory such as `duch`, with `duch-2` for another game; identity stays in metadata. This requires additional directory lookup and collision handling.
4. Accept automatic numeric suffixes for new manual-save collisions and visible rejection of unsupported/reserved names as proposed above?

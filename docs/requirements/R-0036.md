## 1. Summary

1. The user authorized switching the current GPT-OSS 20B worker to high reasoning
   and installing/comparing Qwen2.5-Coder 14B Instruct Q4_K_M, favoring quality
   over speed on the existing 16 GB Mac mini.
2. The main agent owns configuration, comparable task inputs, actual tests and
   review. The local models implement the assigned Java changes. Replayed game
   changes stay isolated; only tooling, configuration and evidence reach main.

## 2. Behavior

1. The GPT-OSS trial uses high reasoning with context 32768 and output 16384.
   Its existing 1800-second attempt, 3600-second task and two-repair limits remain
   unchanged.
2. Qwen uses the exact requested instruction model and Q4_K_M weights. It has no
   GPT-OSS-style reasoning levels; use its supported non-thinking mode rather
   than pretending a high setting has an effect. Initially compare context 32768
   and output 16384 with the same deadlines. Record any resource-driven change
   as a different configuration, not an equivalent result.
3. The existing launcher accepts an explicit profile directory, validates the
   installed model's thinking capabilities and freezes its profile per task.
   The trial temporarily selected high as the default. Its repeated generation
   failures support restoring medium for ordinary work; the exact high and Qwen
   profiles remain explicitly selectable.
   An observed Qwen transport issue is handled by removing and recording one
   outer JSON Markdown fence; arbitrary prose or multiple blocks remain invalid,
   and the existing whole-batch source/path checks still precede any write.
4. Run relation-helper and attack-role assignments at their historical revisions
   for GPT-OSS medium, GPT-OSS high and Qwen. Supply identical role, source,
   requirements, output schema and tests; differences in runtime metadata are
   recorded. Replace entire methods instead of fragile partial-body anchors.
5. Capture actual model identity, context, tokens, duration, attempts, memory
   observations, caller interventions and fresh test reports. Apply the shared
   formatter before testing. Diagnose failures and use targeted worker repairs
   within existing limits; retain rejected candidates and do not weaken tests.
6. A small paired comparison supports a choice for these tasks only. It does not
   establish a general Java success rate or measured Codex-budget savings.

## 3. Implementation steps

1. Add the Qwen comparison profile and supported non-thinking/profile selection
   to the existing launcher, with behavioral checks. Install the requested
   weights and verify model metadata without changing unrelated services.
2. Prepare isolated historical worktrees and shared prompts/tests. Serialize all
   inference and heavy verification; retain per-attempt source snapshots.
3. Verify relation behavior with EuropeanRelationsTest and the page contract;
   verify attack roles with AttackRoleTest, EuropeanHostilityTest,
   EuropeanRelationAiTest and the page contract. Record actual counts and failures.
4. Update the operating evidence and relevant tooling documentation. Run launcher
   and documentation tests and strict MkDocs; commit/push main and verify Pages
   and the development distribution publication.
5. Verified on 2026-10-14: all six task/profile runs completed with documented
   repair dispositions. Medium's relation helper passed 11 checks after one
   repair. High exhausted generation without final code on both tasks. Qwen's
   relation helper failed; its prescribed attack API passed 40 checks after two
   repairs, but full handoff acceptance was withheld because independent review
   found a caller scope contradiction concerning capture. Exact durations,
   failures and limitations are in the [operating evidence](../ai/local-qwen.md#gpt-oss-high-and-qwen25-coder-paired-trial-2026-10-14).
6. The caller handoff rule now requires tracing shared capability callers and
   resolving design/preserved-behavior conflicts before dispatch. This corrects
   future preparation; it does not retroactively remove the experiment's flaw.

## 4. Open questions

1. The bounded results support retaining medium for ordinary work and keeping
   high/Qwen explicitly selectable. General Java reliability and Codex-budget
   savings remain unmeasured; these two tasks cannot establish them.
2. Qwen's 32k context actually loaded on the 16 GB host, with recorded partial
   GPU offload and host swap. This establishes successful execution, not
   exclusive memory use or generally adequate capacity.
3. The attack handoff must not be reused for production until capture behavior
   is resolved and its boundary test included. That is a future gameplay task;
   this experiment integrates no replayed Java candidate.

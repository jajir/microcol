# R-0236 — Promote a verified development build to stable release

1. Status: new
2. Updated: 2026-10-17
3. Related: P32; [development delivery](../development-builds.md), [distribution scope](../distribution.md#distribution-scope-and-remaining-release-work).
4. Dependencies: runtime/platform gates [R-0233](R-0233.md)–[R-0235](R-0235.md), player guide [R-0232](R-0232.md), regression/journeys [R-0208](R-0208.md)–[R-0220](R-0220.md).
5. Primary area: [A01](areas.md#a01).
6. Related areas: A04 save preservation, A03 app entry; P31 evidence.
7. Origin: stable-release promotion beyond already published development builds and Dev launcher; no separate `develop` promotion branch or independent updater is required.

## 1. Summary

1. A specific tested commit becomes an identifiable stable Mac/Linux release with a download, install and recovery path.
2. This requirement owns the release gate and promotion record, not reimplementation of the current development-channel CI.

## 2. Behavior

1. Select one immutable candidate commit/artifact set; verify relevant checks, supported package installs and gameplay evidence, release notes, versions, downloads and checksums. Publish stable artifacts only after required gates pass; record exactly which game build and documentation are live.
2. Test clean install and update from a prior stable candidate while preserving user save/settings files, then rehearse rollback to a known-good artifact if the new candidate fails. Cross-version schema loading remains the explicit R-0240 release-policy question. The Dev launcher remains a distinct development channel and does not silently install a stable release over user data.
3. A failed check, missing platform artifact or mismatched version blocks promotion. Report release status from actual publication/download evidence rather than assuming a push proves availability.

## 3. Implementation steps

1. Define a checklist and promotion mechanism reusing existing `main` CI/artifacts, then verify a candidate with an installation ledger and rollback rehearsal. Link actual publication evidence in existing delivery docs.
2. Current result: captured stable-release process only; ongoing development distributions remain credited.

## 4. Open questions

1. What stable version scheme, download channel and rollback retention period should the first release use? The current Dev-channel rules do not settle these.

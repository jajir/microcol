# R-0253 — Measure four isolated UI test containers

1. Status: ready for development
2. Updated: 2026-10-20
3. Related: P31; [Docker UI tests](../functional-tests.md#docker-ui-tests); no gameplay change.
4. Dependencies: existing Docker runner and [completion callbacks](../ai/completion-callbacks.md).
5. Primary area: [A03](areas.md#a03), supporting developer workflow.
6. Related areas: none.
7. Origin: user explicitly requested trying four independent containers, each running approximately one quarter of the UI tests serially.

## 1. Summary

1. Measure whether four isolated containers shorten the complete regression without losing checks or introducing shared-display interference.
2. Current runner uses one amd64 container, one Xvfb display and serial test JVMs. The host is ARM64 with approximately 8 GiB allocated to Docker; other applications also use that engine.
3. This bounded experiment preserves the production runner and CI gates. Adopting a permanent scheduling change depends on measured results.

## 2. Behavior

1. Run all current UI test classes exactly once across four containers created from the same image. Each container retains its own filesystem, application, settings, display and serial JVM lifecycle.
2. Run the model suite once, in one group. Export independent reports and completion records for all groups, retaining failures and skips as blockers.
3. Record the source revision, class allocation, timing baseline, wall duration and resource observations. A comparison across different machines or revisions is not a controlled speedup measurement.
4. Every group has its own timeout and owned-container cleanup. Completion of fewer than four groups is incomplete; verify the union of reports and investigate missing, duplicate or skipped tests.

## 3. Implementation steps

1. Refine the selected experiment using existing CI XML timings, current test sources, Compose and completion runner. Do not alter tests, assertions, JavaFX lifecycle or global Docker settings.
2. Allocate whole UI classes to four balanced groups; use existing Maven selectors and four completion-runner dispatches with the exact originating task UUID. Store the manifest and source hashes with experiment evidence.
3. Verify the class partition before execution and reconcile actual XML reports afterwards, including current changes relative to baseline. Measure resource usage during execution. Run documentation checks and strict MkDocs for the evidence update.
4. Current result: experiment completed unsuccessfully under the current resource configuration; five suites lost JVMs, and no speedup is accepted. Production adoption and full regression acceptance remain open. See [dated functional evidence](../functional-tests.md#four-isolated-containers-experiment-2026-10-20).

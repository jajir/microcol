# R-0024 — Unload wagon goods using the shared warehouse limit

1. Status: Refining
2. Updated: 2026-10-13
3. Related: P10, P08; COL-008/010, CARGO-009; UC-023/UC-036 (Hra). See the [rule catalogue](../gap-analysis.md),
   [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: Published Z01 model transaction; existing wagon and colony access.
5. Primary area: [A07](areas.md#a07).
6. Related areas: A06 ground transport; A03 quantity confirmation.

## 1. Summary

1. Extend the safe unloading journey to a wagon arriving at its owner’s colony, reusing the protection already delivered for ships.

2. Existing capability: Z01 supports own ship→own colony and warehouse limits. A wagon fixture loaded into the model but map rendering failed with an unsupported WAGON image request. TC22/TC_04 isolates the image-provider gap while still opening an ordinary colony; this is not a wagon-unloading UI acceptance test. Source inspection also finds ship-only dock controls. The image asset exists, but its type/instance provider registration is missing.

3. Wagon→owned colony unloading of non-food goods. Do not reimplement warehouse capacity, change food/growth, add trade routes or permit wagon passengers.

## 2. Behavior

Target behavior for later implementation. The audit below separates existing
capability from missing steps; it does not accept these complete targets.

1. A wagon at an eligible owned colony is discoverable in that colony’s carrier controls, with its cargo accessible for unloading.

2. At capacity 100 with 90 ore stored and 30 aboard, the preview offers 10. Accepting transfers 10, leaving 100 in storage and 20 aboard.

3. Cancel transfers zero. A full warehouse offers no positive amount and explains the limit; a warehouse upgrade uses the model’s current larger capacity.

4. Wrong owner, remote wagon or changed cargo/warehouse state rejects before mutation. The UI refreshes the quantity instead of losing the remainder.

5. Save/load preserves wagon location and both inventories; the existing ship unloading journey remains unchanged.

## 3. Implementation steps

1. First connect wagon artwork to the image provider and expose a wagon through colony carrier controls. Reuse Z01 capacity calculations, but inspect its ship-only transfer eligibility before extending it; existing ship acceptance does not prove wagon support.

2. Connect wagon selection and quantity confirmation to the same model transaction, preserving cargo conservation and current owner/location checks.

3. Proposed `TC_wagon_unload_capacity_test` mirrors boundary quantities but uses an actual wagon journey. Run existing Z01 scenarios; model tests cover wagon eligibility and stale capacity.

4. Verification: TC22/TC_04 passed on 2026-10-13: the ordinary colony opens, but WAGON type artwork is null and an instance/direction image request throws. This diagnostic probe isolates the earlier map-render failure; it does not claim wagon travel or unloading works. Final suite commands and publication evidence are maintained in the [functional test record](../functional-tests.md#free-play-audit-2026-10-13).

## 4. Open questions

1. Should ships and wagons share one carrier list or separate labeled groups? Blocking: no for the audit. Proposed implementation: reuse the existing carrier list with a recognizable wagon image; verify discovery and selection when adding support.

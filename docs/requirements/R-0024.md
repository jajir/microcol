# R-0024 — Unload wagon goods using the shared warehouse limit

1. Status: Published
2. Updated: 2026-10-13
3. Related: P10, P08; COL-008/010, CARGO-009; UC-023/UC-036 (Hra). See the [rule catalogue](../gap-analysis.md),
   [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: Published Z01 model transaction; existing wagon and colony access.
5. Primary area: [A07](areas.md#a07).
6. Related areas: A06 ground transport; A03 quantity confirmation.

## 1. Summary

1. Extend the safe unloading journey to a wagon arriving at its owner’s colony, reusing the protection already delivered for ships.

2. Baseline before this change: Z01 supported own ship→own colony and warehouse limits. A wagon fixture loaded into the model but map rendering failed with an unsupported WAGON image request. TC22/TC_04 isolated the image-provider gap while still opening an ordinary colony; this is not a wagon-unloading UI acceptance test. Source inspection also found ship-only dock controls. The image asset existed, but its type/instance provider registration was missing.

3. Wagon→owned colony unloading of non-food goods. Do not reimplement warehouse capacity, change food/growth, add trade routes or permit wagon passengers.

## 2. Behavior

Implementation is authorized by the active R-0019-and-later goal. These
manual-backed decisions define acceptance; the implementation has passed targeted checks and the complete main-branch regression.
Publication was verified as `dev-54-13001e6ac6b8` on 2026-10-13.

1. A wagon at an eligible owned colony is discoverable alongside ships in the existing carrier controls, with a recognizable wagon image and its own cargo shown when selected. Map/status names work in English and Czech. Wagons carry goods only; an attempted passenger transfer or dragging its carrier icon must not cause a UI exception or put it aboard a ship.

2. At capacity 100 with 90 ore stored and 30 aboard, the preview offers 10. Accepting transfers 10, leaving 100 in storage and 20 aboard.

3. Cancel transfers zero. A full warehouse offers no positive amount and explains the limit; a warehouse upgrade uses the model’s current larger capacity.

4. Wrong owner, remote wagon or changed cargo/warehouse state rejects before mutation. The UI refreshes the quantity instead of losing the remainder.

5. Save/load preserves wagon location and both inventories; the existing ship unloading journey remains unchanged.

## 3. Implementation steps

1. Integrated into `main` after targeted verification: register the existing `ImageLoaderUnit.IMG_UNIT_WAGON` for type and instance/direction requests, and add the three wagon-name keys to `UnitTypes` and both resource bundles. Extend the colony carrier query from `List<Ship>` to owned `UnitWithCargo` units at the colony, retaining order, and remove the corresponding raw cast in `PanelColonyDockBehaviour`. The shared dock already displays cargo carriers but its icon drag handler asserts ship type: attach that handler only to ships, preserving their existing behavior.

2. Reuse the existing warehouse dialog and `ColonyWarehouse.getUnloadableGoods`/`moveToWarehouse` transaction. Source inspection on 2026-10-13 confirms that eligibility is already carrier-generic: cargo type/quantity, matching owner, live carrier at the colony, and remaining storage are checked before mutation. Do not duplicate the limit or weaken those guards. Passenger eligibility remains in the existing shared model operations and requires a ship.

3. Add `TC_31_F23_wagon_unloading_test` with an F23 fixture: move a real loaded wagon into its colony, select it among existing carriers, offer 10 from 30 ore with 90 in storage, cancel, confirm, show full-storage feedback, and verify 100/20 after save/Continue. Cover an upgraded warehouse and changed capacity/cargo while the amount dialog is open, keeping the remainder. Model tests use a real wagon for owner/location/live membership, capacity and unchanged-state rejection; verify that it cannot carry passengers. Preserve existing Z01 ship scenarios and update the TC22/TC_04 diagnostic from expected artwork failure to supported artwork without changing its stable ID.

## 1. Summary

1. The player needs starvation to remove the agreed resident and update production and warnings consistently.

2. Migration observation (2026-10-14): Colony already kills one random internal worker when projected food is negative and resets food to zero, then recomputes production. Existing famine journeys do not prove every boundary and victim role.

3. Scope: the outcome and examples below. Selected and refined on 2026-10-16; it does not reopen the delivered origin scope or close a whole UC.

## 2. Behavior

Agreed acceptance, refined on 2026-10-16; inherited resolved decisions remain agreed.

1. Exactly zero food after production/consumption → no starvation death. A negative result → exactly one internal resident dies under the retained random-victim policy.

2. The deceased worker contributes no subsequent production; any surviving producer consumes only available input and no stock becomes negative.

3. The report identifies famine and the loss once; visiting units and cargo passengers are not selected as internal famine victims.

4. With different possible victim jobs, preview and final report explain the resulting stocks. Save/load must not replay an already processed famine.

5. Accepted behavior (2026-10-15; [economy, production and education](../gap-analysis.md#economy-production-and-education)): Retain random internal famine victims, recompute committed production from survivors and distinguish the variable preview from the final report.

6. Shared update boundary (2026-10-15): apply this requirement within [national turn processing](../gap-analysis.md#national-turn-processing). Resume the saved completed boundary without repeating production, arrivals or action replenishment; future pending choices must preserve earlier completed updates.

## 3. Implementation steps

1. Keep famine resolution in `Colony.startTurn` and shared production queries. Predict food with current residents; zero is safe, negative selects exactly one random internal worker. After removing that worker, reset opening food to zero and recompute all committed production/consumption from survivors, clamping final food at zero without a second victim. Preserve the R-0058 growth phase and ordinary production/input limits; the separate expert-throughput correction belongs to R-0061.

2. Source inspection on 2026-10-16 found that nonfood production is recomputed after a death but food remains unconditionally zero. Repair this discrepancy without duplicating production formulas. Keep the existing random source, allowing controlled test selection through the current construction/test seam. Verify outdoor-food, outdoor-input and indoor-producer victims with hand-calculated survivor results, as well as exact zero, insufficient survivor food, outside visitors and cargo passengers.

3. In the existing colony production display, visibly explain that famine makes forecast output uncertain. Record the actual lost resident and final stocks in the existing famine event/report, with a persisted immutable snapshot so later inventory changes or save/load cannot rewrite history. Render localized player-facing text using existing report controls; do not put game calculations in the UI. Update current-schema event fixtures directly where necessary. Last-resident removal and ship destinations are R-0060; retain that path while recording one famine loss.

4. Extend `TC_09` and `TC_10` with named page-object verification for warning/report and survivor accounting; retain their IDs and English player steps. Cover completed-boundary save/continue and report count in model persistence tests. Run focused Docker model/UI and page-contract checks, shared Java formatting and full integrated regression before completion. No new TC ID is allocated. The user authorized cloud Sol workers for this batch; implementation is queued, not yet verified.

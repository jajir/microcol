## 1. Summary

1. Players should be asked to save only when an operation would discard unsaved game state. Opening settings or inspecting a loaded game should not produce unnecessary save prompts.
2. Source inspection at `36a4d559` on 2026-11-01: `PersistingService.confirmLeave` asks for every ready, unfinished game. The existing navigation contract explicitly defers change detection. This is source evidence, not a fresh runtime test.
3. Scope: saving policy and change detection across existing exit paths. The user accepted the preceding proposal on 2026-11-01; see the [agreed save policy](../save-load-navigation.md#pravidla-ukladani-schvalena-1-listopadu-2026). Per-turn autosave rotation is requested separately in [R-0388](R-0388.md), whose five-save retention and failure/replay rules were accepted on 2026-11-01. No gameplay implementation was requested.

## 2. Behavior

1. A successfully loaded game starts unchanged. Moving the camera, selecting units, opening menus, settings or informational panels does not make gameplay unsaved. Successful gameplay mutations do: movement, orders, trades, colony changes and turn processing, including changes that do not move a unit. Rejected/canceled actions do not. Application preferences are saved independently; any future setting that changes this particular game's rules counts as gameplay.
2. Returning to the main menu, quitting, closing the window, restarting or activating another validated save uses one rule: if the current playable state is safely saved, continue without a prompt; otherwise offer **Save and continue / Leave without saving / Cancel**. Cancel and Escape keep the current game and screen. Browsing the load screen alone does not discard the game. Keep existing finished-game behavior under [R-0374](done/R-0374.md).
3. A successful manual save, quick save or automatic checkpoint covering the current complete gameplay state makes that state saved. A failed/canceled save does not. Saving and then only inspecting the map must allow exit without another prompt. A later gameplay change requires protection again. Loading an earlier save makes that loaded state the new baseline, without rewriting the source.
4. User correction on 2026-11-01: choosing **Save and continue / Yes** opens the regular manual Save dialog so the player chooses the named destination or explicitly confirms an overwrite. This applies equally to Command+Q, window close, menu exit, restart and replacement by another game. Do not substitute a silent autosave/latest-position write. Continue the original leave action only after the chosen save completes successfully. Cancel, Escape, closing the Save dialog or write failure keeps the current game and window open; failed saving never counts as agreement to leave without saving. The loaded/imported source is never silently overwritten. An incomplete turn cannot be declared safely saved.
5. Keep **Save** as a named snapshot, with explicit confirmation for overwriting an existing manual save. **Quick save / F5** replaces only `~/.microcol/saves/<playthrough-id>/quick.microcol` (renamed consistently to `~/.akropia/saves/<playthrough-id>/quick.akropia` by [R-0389](R-0389.md), without changing this save policy); show success or failure. Each new playthrough has its own identity, while loading retains that identity. Loading an older save of the same playthrough and pressing F5 therefore replaces its newer quick save; named snapshots remain intact. Quick load continues to use that playthrough's quick slot.
6. With autosave enabled, save at the safe human-turn-start boundary after AI/world processing and before player control, plus the agreed decade checkpoint. Never save each unit move or an incomplete turn. [R-0388](R-0388.md) owns the newly requested rolling history. Long turns still depend on quick/manual saves for crash protection.
7. For a new game, recommend an initial safe checkpoint before player control when autosave is enabled. Then immediate exit needs no prompt. If autosave is disabled or the initial write fails, the generated game has never been saved: offer to preserve it even before its first move. Explain that this prompt protects the generated starting world; do not pretend it already has a recoverable file. Loading an existing save and immediately leaving never needs a prompt while that saved state remains available.
8. Opening/closing settings neither saves nor asks to save gameplay and keeps the live game available. Exiting the application from settings still uses the shared protection rule. Leaving without saving does not delete existing autosaves or named saves; Continue follows the existing last successful save/load rule and does not promise to restore discarded changes.

## 3. Implementation steps

1. Refine after selection for development; chapter 2 was accepted on 2026-11-01. Follow the [package map](../architecture.md): gameplay state belongs to model/store and the campaign envelope; navigation and confirmation belong to GUI. Reuse `PersistingService`, the existing turn-checkpoint path and save failure handling. Do not infer changes from a completed turn count or unit movement alone.
2. Decide the smallest reliable way to compare saved gameplay state or track all successful mutations. Exclude transient UI state and save metadata. Review all callers, turn processing, loading, manual/quick/checkpoint writes and restart/menu/window-close paths. Only successful persistence of the current state establishes a saved baseline; cover deleted or unavailable baseline files during refinement.
3. Extend existing save/recovery UI scenarios and add named cases during refinement for load→inspect→exit, save→exit, mutate→exit, settings round-trip, initial unsaved game, autosave success/failure, canceled dialogs and same-playthrough quick-save replacement. Include model/service checks for missed mutations and failure atomicity. Gameplay implementation requires model/JUnit, targeted Docker UI and smoke acceptance; this proposal requires documentation checks and strict MkDocs only.
4. Current result: proposal captured; no executable changes or runtime acceptance. Comparative references consulted 2026-11-01: [Factorio settings](https://wiki.factorio.com/Settings) documents three rolling autosave slots; [RimWorld save files](https://rimworldwiki.com/wiki/Save_file) documents named manual saves and numbered autosaves; [RimWorld modes](https://rimworldwiki.com/wiki/AI_Storytellers#Commitment_mode) distinguishes reload-anytime and commitment. These illustrate save categories, not evidence that either game uses the proposed MicroCol prompt rules.

5. Selected for implementation on 2026-11-01 after the archive/preview phase. Use the existing persistent gameplay snapshot and production Gson adapters to compare gameplay state against a successful save/load baseline, excluding save name, archive metadata and transient UI state. Prefer structural JSON equality or an equivalently deterministic representation over a new per-action dirty flag scattered across mutations. Audit persisted view fields and normalize only genuinely non-gameplay fields. Do not serialize incomplete turns or mark their state safely saved.
6. Keep the baseline associated with the actual saved file. A missing, unreadable or replaced backing save must not silently count as recoverable current state. Failed save/load leaves the old baseline and current game intact. Successful loading establishes the loaded state only after validation and activation, without writing the source; successful manual/quick/automatic save of the same state establishes protection. Restart, menu, window close and confirmed load reuse the same policy. Save-and-continue opens the existing manual Save flow and returns success only after an actual successful save; propagate cancel/failure to every leave caller. No automatic recovery destination substitutes for the chosen manual destination.
7. Include named player scenarios for quit/close → Yes → Save dialog → successful named save → leave, plus cancel/Escape/write failure keeping the game open and no silent recovery write. Verify the shared quit handler in Docker and platform shortcut selection in model tests; native macOS remains optional manual-only. Add focused state/persistence tests for mutations without movement, rejected/canceled operations, transient selection/camera/settings, save success/failure, load success/failure, missing backing files and unfinished turns. Extend existing TC191/TC42/TC43 with named scenarios for load-inspect-exit without prompt, mutate-exit with all three choices, save-exit, settings round-trip and initial autosave off/failure. Preserve earlier scenario IDs and adjust obsolete always-prompt expectations to the agreed policy while retaining protection assertions. Run focused model/UI checks; full combined tests and smoke remain deferred under the expanded-batch amendment.

# R-0314 — Lake animation proposals in screenshot context

1. Status: new
2. Updated: 2026-10-27
3. Related: [UC-114/119](../use-cases.md), [visual brief](../graphics.md#soucasne-zadani-vzhledu) and [lake proposal catalogue](../graphics.md#animace-jezera-navrhy-27-rijna-2026).
4. Primary area: [A03](areas.md#a03), shared visual language and map presentation.
5. Dependencies: A05 owns lake identity, coasts and resource visibility; A04 owns navigation and Continue. [R-0293](done/R-0293.md) and [R-0305](done/R-0305.md) supply the existing sea animation and black contours.
6. Origin: on 2026-10-27 the user reported miniature lake shapes appearing inside a lake and requested seven expanding-ring alternatives and seven small-wave alternatives, animated in the supplied screenshot before choosing a design.

## 1. Summary

1. Decorative motion should make the lake surface feel alive without drawing another lake inside it. Its shoreline and meaningful map symbols must remain readable.
2. Deliver fourteen comparable proposals using the user's actual map crop, including units, fish and grid. Isolated artwork does not provide enough context for this choice.
3. This request authorizes proposal preparation. No alternative is selected for runtime implementation.

## 2. Behavior

1. The [proposal catalogue](../graphics.md#animace-jezera-navrhy-27-rijna-2026) contains K1–K7 expanding rings and V1–V7 small waves. Each uses the same screenshot context, a six-second comparison cycle and a transparent line motif without a filled miniature lake.
2. The interactive comparison offers pause/resume and the supplied 2× detail or 1× game scale. Archived GIFs preserve every alternative's movement and context. Their repeated cycles demonstrate appearance; they do not establish the eventual frequency of lake decoration in the game.
3. Future implementation should preserve lake identity, coast shape, terrain colour, fish/resource priority, hidden-map behavior, navigation, Continue and gameplay outcomes. Motion remains cosmetic, quiet and understandable without sound.
4. Only the selected alternative will be refined for implementation. Existing sea behavior is a reference and remains unchanged by these proposals.

## 3. Implementation steps

1. Source inspection at `121b08aa` identifies the cause: `ImageRandomProvider` gives lakes intermittent water decoration, but its animated frame branch covers only `OCEAN` and `HIGH_SEA`. Lakes fall back to `drawing-LAKE` in `terrain-symbols.svg`, a filled lake silhouette reused in the transparent decoration row. `PaintService` draws that silhouette over the lake background before coast overlays.
2. Existing sea animation has 120 frames over six seconds. V4 reuses those actual atlas frames at 70% size; other proposals use new line geometry. The map crop is a composited preview with the lower water plane restored, not a screenshot of implemented JavaFX behavior. Keep proposal assets in documentation, separate from runtime assets.
3. After selection, follow the [package map](../architecture.md): reuse `gui.image`, the existing map animation clock, atlas/export conventions and painter ordering. Review `ImageRandomProvider`, `ImageLoaderTerrainSymbols`, `ImageProvider`, `MapManager`, `PaintService`, the terrain SVG/PNG and static terrain/help previews together. No model or AI dependency changes are needed.
4. A later runtime change needs `SelectedTerrainArtworkTest`, `TerrainDecorationTest` and the existing `TC_80_F72_terrain_identity_test.TC_04_sparse_terrain_and_living_water_survive_pan_and_continue` journey extended through dedicated page verification methods. Cover frame progression, rest/loop boundaries, coasts, resource priority, static rendering, hidden terrain and Continue. Apply shared Java formatting and all local acceptance phases required by the [functional contract](../functional-tests.md).
5. Proposal verification and documentation acceptance belong to the [dated evidence](../publishing.md#lake-animation-proposals-2026-10-27). They do not establish game implementation, runtime acceptance or publication.

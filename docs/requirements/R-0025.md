# R-0025 — Enforce population and prerequisites when choosing construction

1. Status: Published
2. Updated: 2026-10-14
3. Related: P12; BUILD-001/002, BUILD-016/019; UC-042/049 (Hra). See the [rule catalogue](../gap-analysis.md#construction-upgrades-and-building-effects), [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: Existing construction queue and [building matrix](../gap-analysis.md#building-data-matrix). Use the current colony completion phase; a general turn-phase rewrite remains [R-0002](R-0002.md).
5. Primary area: [A07](areas.md#a07).
6. Related areas: A03 project availability; A04 queue persistence; A07 population/resources.

## 1. Summary

1. Make construction discoverable and prevent the player or AI from starting an ineligible building project through a lower-level queue operation.

2. Baseline: `Colony.css` hides `#id_carpenter`. TC22/TC_05 verifies this gap and the unchanged empty queue. `ColonyBuildingQueue` omits population from its query and checks only duplicate type on addition. Its insertion can mutate before discovering a missing destination; save groups buildings before units instead of preserving their order. These are source findings, not accepted behavior.

3. Scope: currently represented building projects, their population/predecessor checks, queue integrity, completion prerequisites and player feedback. Correct the existing metadata needed by these checks; do not add missing building types, Founding Father acquisition, rush purchasing or a new hammer-retention policy. Factory/Custom House founder gates and other unimplemented building effects remain explicit catalogue gaps, not claims of full manual parity.

## 2. Behavior

Implementation is authorized by the active R-0019-and-later goal. The decisions
below are implemented from the manual references in chapter 4; chapter 3 records
the current verification and delivery state.

1. A new project requiring population N is unavailable at N−1 and available at N only with its existing predecessor and other supported requirements. Population is a start condition: after an eligible project has entered the queue, a later population decrease does not discard or pause it. Use internal colony residents, not visiting people or passengers.

2. UI and direct model calls use one eligibility query. Registered type, live colony/current owner, initial versus paid building, existing upgrade chain, queued duplicate/incompatible upgrade, predecessor and population are checked before admission. Invalid additions, insertions and moves leave queue order, IDs, progress, stocks and treasury unchanged. Do not use a partial mutation followed by an exception or a silent null result as rejection.

3. The colony has a visible, localized construction control. The picker shows the project, hammer/tool cost and a readable reason for missing population or predecessor. Choosing an option does not itself change the queue; explicit confirmation adds it once. Cancel/Escape leaves the existing project and progress unchanged. Recheck before confirmation if the colony changes while the picker is open. Preserve usable queue ordering/removal and the existing supported unit queue rather than exposing a buildings-only replacement that loses those operations.

4. Before completing, revalidate the colony, current predecessor and whether the target already exists; an invalid live prerequisite leaves the project visibly waiting and consumes no tools. Do not reapply the population start gate. With all required hammers but one tool short, retain progress and explain the missing tools; after supplying the final tool, complete once, deduct exactly the required amount, replace the predecessor and remove only the completed queue entry. Reopening a view or loading the game does not complete it again.

5. Save/load preserves exact queue order, entry identity and progress, including a mixed unit/building queue. Reject unknown/missing kinds or types, malformed IDs, negative progress and duplicate/incompatible entries. A known project with a temporarily missing predecessor remains visibly waiting instead of being silently made eligible; a lower current population alone is valid because the project was already admitted. Reading a save never changes the file or runs construction effects.

## 4. Open questions

1. Resolved on 2026-10-13: use population as a start gate, not a completion gate. The [original manual](../Sid_Meiers_Colonization_manual.pdf), printed pages 48–49 and 52 (PDF 54–55 and 58), describes population-dependent project selection and tools needed at completion. The Building Chart (PDF 134) explicitly defines population as required to start. Continuing an admitted project after population loss is the chosen interpretation of that distinction; the manual does not separately describe that edge case. This replaces the earlier unresolved pause proposal.

2. Resolved on 2026-10-13: reject malformed references/identity/progress and incompatible queue data; retain a structurally valid project with a current missing predecessor as visibly waiting. A population decline does not invalidate prior admission. These save-data rules are MicroCol policy implementing atomicity and continuity; they are not a historical save-format claim. Backward compatibility is not required.

3. Resolved on 2026-10-13: for Newspaper, use the Building Chart’s population 4 (PDF 134) as the numeric project contract despite prose on printed page 58 (PDF 64) discussing population 1. Retain that disagreement in the catalogue. The same chart fixes the carpenter cost/chain, Fort threshold and Church tools. Factory/Custom House founder acquisition and unimplemented building effects remain outside this construction-eligibility slice; do not label this requirement acceptance of all BUILD rules.

# R-0025 — Enforce population and prerequisites when choosing construction

1. Status: Draft
2. Updated: 2026-10-13
3. Related: P12; BUILD-001/002; UC-042 (Hra). See the [rule catalogue](../gap-analysis.md),
   [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: Existing construction queue and building matrix; [R-0002](R-0002.md) completion phase.
5. Primary area: [A07](areas.md#a07).
6. Related areas: A03 project availability; A04 queue persistence; A07 population/resources.

## 1. Summary

1. Prevent a player or AI from selecting an ineligible building project through a lower-level queue operation.

2. BUILD-001 records missing population enforcement in queue eligibility and `addAtEnd`. BUILD-002 already implements hammer/tool-gated completion; preserve that working behavior.

3. Eligibility for currently supported building projects, enforced at model entry points and shown in the queue UI. Missing building types, changed hammer retention and rush purchasing remain separate.

## 2. Behavior

Proposed acceptance for individual refinement; capture does not approve implementation.

1. A project requiring population N is unavailable at N−1 and available at N only when its predecessor and other supported requirements are met.

2. Both UI and direct model calls use the same eligibility. Rejected addition leaves the queue, progress, stock and treasury unchanged.

3. The picker explains a missing population or predecessor. Cancel leaves the previous project selected; duplicate or incompatible upgrade requests remain rejected.

4. Before completion, revalidate the agreed live prerequisites. With enough hammers but one tool short, preserve progress; supplying the final tool completes once and deducts exactly the required tools.

5. Save/load preserves queued project identity and progress; it does not legalize invalid current-schema queue data silently.

## 3. Implementation steps

1. Inspect `ColonyBuildingQueue`, `ConstructionType` and `gui.screen.colony.buildingqueue`; share eligibility between query and mutation instead of copying checks.

2. Compare supported projects against the existing building matrix; resolve inconsistent prerequisite/population rows before adding acceptance values. Apply the chosen population-loss policy.

3. Proposed `TC_construction_eligibility_test` uses one upgrade reachable from ordinary colony growth. Parameterized model tests cover supported project boundaries, missing predecessor, one-tool-short completion and invalid restored queue.

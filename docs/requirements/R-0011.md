# R-0011 — Enforce the model dependency boundary with ArchUnit

1. Status: Published
2. Updated: 2026-10-13
3. Related: [P31 quality](../implementation-plan.md#seznam-pracovnich-baliku),
   [package responsibilities](../architecture.md). Architecture support, no new gameplay rule.
4. Dependencies: existing Maven/JUnit tests; remove current reverse dependencies.
5. Primary area: [A05 — World, units and orders](areas.md#a05), the shared model foundation.
6. Related areas: A04 persistence, A08 AI and A10 mission outcomes. This explicitly
   requested P31 safeguard applies across areas; it does not change the proposed
   A01 refinement priority or accept any of the ten gameplay drafts.

## 1. Summary

1. The user requested ArchUnit and an automatic check that everything in
   `org.microcol.model`, including subpackages, is independent of other game packages.
2. Inspection of baseline `44785516` on 2026-10-13 found model dependencies on
   GUI exceptions/persistence, mission dialog and translation types, and AI
   continent analysis. The first executable rule reported 32 violations.
3. Scope is the test dependency, a mandatory model boundary check and the
   refactoring needed to satisfy it. Preserve gameplay, translations, save paths,
   campaign progress and opponent decisions. Do not add a legacy allowlist.

## 2. Behavior

1. During normal Maven tests, compiled production classes in `org.microcol.model..`
   must have no dependency on any `org.microcol..` class outside that subtree.
   Tests may still use UI fixtures and mocks; they are excluded from imported
   production classes. Direct JavaFX dependencies are also forbidden; Java and
   other third-party libraries remain allowed.
2. The rule covers dependencies in signatures, inheritance, annotations and
   method/field access, including all model subpackages. Empty imports must fail.
3. Shared model data and persistence helpers belong in model packages. Opponent
   target selection stays in AI. Mission events carry model identifiers; UI
   translates and displays them with the same text and sequence.
4. ArchUnit is a test-scope dependency only. Existing `mvn test` and the required
   CI functional job run the guard; a violation blocks publication.

## 3. Implementation steps

1. Add ArchUnit core to `microcol-game` and a regular JUnit Jupiter architecture
   test compatible with the existing test engine. Demonstrate failure against
   the real baseline before removing its violations.
2. Remove the reverse dependencies and update affected callers, package
   responsibility descriptions and links. Preserve the existing AI policy.
3. Check mission identifiers/translations, persistence paths and continent
   analysis with focused unit regressions, then run the complete game test suite.
   Use existing campaign/free-play/save-load functional scenarios in required CI.
4. Apply the shared Java formatter, build documentation strictly, review changes,
   commit and push main. Verify documentation deployment and development release.

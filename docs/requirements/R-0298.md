# R-0298 — Manage saved games through a coherent in-game journey

1. Status: new
2. Updated: 2026-10-26
3. Related: P26, SUPPORT-001, UC-113 (Hra); P28 and UC-119 (Regrese). See [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: [R-0067](done/R-0067.md) safe load failure, [R-0068](done/R-0068.md) checkpoints and atomic writes; existing manual Save/Load and Continue.
5. Primary area: [A04](areas.md#a04).
6. Related areas: A01 main/in-game menu and exit routes; A03 accessible lists, confirmation and failure feedback; A10 retirement remains separate under [R-0194](done/R-0194.md).
7. Origin: user request on 2026-10-26 for a PlantUML map of save/load screens and transitions. Documentation is authorized; gameplay implementation has not been selected.

## 1. Summary

1. Players need an understandable path to find, save, resume and manage their games without losing current progress by accident.
2. Current source already implements manual file dialogs, Continue, three recovery points and atomic saving. The missing outcome is a coherent in-game journey, not serialization itself. The [navigation proposal](../save-load-navigation.md#co-uz-existuje) records the inspected revision and current limitations.
3. This capture owns the proposed saved-game interface and its navigation. It preserves checkpoint frequency, current development save compatibility policy and retirement semantics. Cloud storage, quick-save shortcuts and additional rotating checkpoints are outside scope.

## 2. Behavior

1. Proposed: main-menu Continue and Load, and an in-game menu offering Save, Load and exit, share the [screen and transition diagrams](../save-load-navigation.md). These are proposals, not accepted runtime behavior.
2. Proposed: list manual positions and existing recovery points with identifying metadata; create a named position, explicitly confirm overwrite or manual deletion, and return to the caller on cancellation. Preserve access to the existing external-file picker.
3. Proposed: a shared unsaved-progress confirmation protects replacing the current game, returning to the main menu and closing the application. Save failure prevents the pending transition; load failure preserves the original game and source file. Continue is distinct from closing the in-game menu.
4. Retain agreed Unicode text limits, atomic replacement, read-only inspection, recovery cadence and rejection of invalid required save data. Empty/unreadable lists, invalid names, missing files, failures and keyboard cancellation have explicit routes in the proposal. No historical-save migration is implied.

## 3. Implementation steps

1. The requested documentation consists of one authoritative Czech navigation page, five editable PlantUML sources and their rendered SVGs. [Documentation evidence](../publishing.md#r-0298-save-load-navigation-2026-10-26) records checks; implementation and player validation remain unperformed.
2. Refine only when selected for development. Reuse ownership from the [architecture map](../architecture.md): GUI screen/dialog coordination, existing `PersistingService`, `GameController`, `PersistingTool`, recovery settings and atomic model persistence. Keep validation authoritative and avoid new model-to-GUI dependencies. Define safe activation and the last-position update before assigning implementation.
3. Future acceptance extends existing `TC_42_F34_load_recovery_test` and recovery-checkpoint scenarios under R-0068, plus named scenarios for new save, overwrite cancellation, deletion, unsaved exits, close-window protection and failures. Follow the [functional contract](../functional-tests.md). No gameplay test is claimed for this documentation-only delivery.

## 4. Open questions

1. Should the proposed shared Save / Discard / Cancel confirmation replace today's automatic last-position save on exit to the menu? Blocking: yes for implementation of exit behavior; the navigation page explicitly remains a proposal until this change is accepted.

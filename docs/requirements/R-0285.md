# R-0285 — Distinct unit artwork on the game map

1. Status: new
2. Updated: 2026-10-25
3. Related: [visual brief](../graphics.md#soucasne-zadani-vzhledu), [unit help R-0284](done/R-0284.md); this capture and proposal study claims no gameplay UC acceptance.
4. Dependencies: current 35 unit identities, equipment and artillery damage state; [R-0260](done/R-0260.md) visual agreement and [R-0277](done/R-0277.md) terrain treatment.
5. Primary area: [A03 — screens and shared UI language](areas.md#a03).
6. Related areas: A05 owns unit identity and map visibility; A07 owns professions; A09 owns combat equipment and damage meaning. Artwork consumes those facts without changing rules.
7. Origin: on 2026-10-25 the user requested the current unit appearance followed by ten alternatives showing how the units could look on the game map.

## 1. Summary

1. Let the user compare the actual current unit pictures with ten coherent visual families before choosing future artwork.
2. Give existing unit types recognizable silhouettes at map scale, consistent with the agreed pen drawing and flat palette.

## 2. Behavior

1. The current overview shows all 35 unit types, identifies shared pictures and separates equipment or damage variants from unit types.
2. Each proposed family covers those 35 types plus four colonist equipment variants and damaged artillery. The comparison includes small previews in 45 × 45 px spaces.
3. The study is a proposal, not a change to unit capabilities, ownership, visibility, selection or movement. Profession props must not misrepresent actual gameplay equipment in a future implementation.
4. Final artwork must retain readable silhouettes and conform to the authoritative visual brief. Generated shading or excess detail is not an approved style exception.

## 3. Implementation steps

1. The [proposal gallery](../graphics-unit-proposals.md) contains the source-resource inventory, ten generated families, a fixed-size comparison and exact generation prompts. [Documentation evidence](../publishing.md#unit-map-proposals-2026-10-25) records its verification.
2. After the user selects a direction, refine only this requirement for implementation. Reuse the existing gui.image ownership, editable SVG and runtime image pipeline; share the selected artwork with map and unit help.
3. Before implementation, settle visual precedence between profession and actual equipment, retain the model as authority, and select the affected named TC scenarios under the [functional contract](../functional-tests.md). No runtime files or gameplay tests change in this proposal-only task.

## 1. Summary

1. The player needs to learn from the turn report that completed hammer work is waiting for tools, without repeatedly opening every colony.

2. Migration observation (2026-10-14): R-0025 supplies completion gating and a visible waiting reason. The turn report still lacks the missing-tools advisor event; this is distinct from the working queue display.

3. Scope: the outcome and examples below. Selected on 2026-10-16; the user accepted per-turn notification on 2026-10-17; it does not reopen the delivered origin scope or close a whole UC.

## 2. Behavior

Acceptance refined on 2026-10-17; inherited resolved decisions remain agreed.

1. A project has enough hammers but is one tool short → do not finish it; show an actionable missing-tools report identifying colony, project and shortage.

2. Opening the colony from that report shows the same retained progress and waiting reason.

3. Supply the last required tool → complete once on the agreed phase and consume exactly the required tools.

4. Accepted frequency (user decision, 2026-10-17): produce one missing-tools report each owner turn while the project is still waiting for tools. Repeated views, dismissal and Continue do not create another report for the same update or duplicate completion. The next owner turn reports the current shortage again; reminders stop when the project no longer waits for tools.

5. Accepted behavior (2026-10-15; [recovery and presentation](../../gap-analysis.md#recovery-and-presentation)): Keep the missing-tools outcome visible through the shared report controls with the per-turn frequency accepted on 2026-10-17.

6. Shared update boundary (2026-10-15): apply this requirement within [national turn processing](../../gap-analysis.md#national-turn-processing). Resume the saved completed boundary without repeating production, arrivals or action replenishment; future pending choices must preserve earlier completed updates.

## 3. Implementation steps

1. `ColonyBuildingQueue.startTurn` owns completion after production. At each normal construction phase, emit a missing-tools event for an otherwise eligible head with sufficient hammers and insufficient tools, without spending resources. Keep existing phase ordering, save boundaries and once-per-owner-update processing; no persisted waiting-episode suppression is needed. Viewing, dismissal and Continue never execute construction processing.

2. An immutable event through `TurnEventProvider`, `TurnEventStore` and `TurnEventPo` retains colony identity/name, typed project identity and actual missing quantity. GUI processors translate the snapshot in English/Czech. A keyboard-accessible Open colony action reuses screen navigation and rechecks the current game and owned colony. Closing or opening the report spends nothing; stale reports cannot disclose another owner's colony.

3. `ConstructionWaitingReportTest` covers hammer/tool boundaries, consecutive owner updates with current shortage, no completion or resource consumption while waiting, exact completion, unit projects, report roundtrip and malformed event rejection. TC32/TC02 verifies English keyboard navigation, save/Continue without a same-update duplicate, another waiting turn with a fresh reminder, then last-tool completion. TC08 covers Czech/mouse and readable layout; TC09/TC10 reject stale colony/game actions. Preserve construction/save/rush checks and `PageVerificationContractTest`; run full Docker regression and strict docs validation.

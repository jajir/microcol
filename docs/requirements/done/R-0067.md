## 1. Summary

1. The player needs a failed Load or Continue to leave the current game and existing save usable.

2. Current situation: R-0013/R-0018 verify successful save and Continue. Corrupt, unreadable or invalid saved-game recovery was explicitly outside that slice.

3. Scope: the outcome and examples below. Selected and refined on 2026-10-16 under the remaining-backlog authorization; it does not reopen the delivered origin scope or close a whole UC.

## 2. Behavior

Acceptance refined on 2026-10-16; inherited resolved decisions remain agreed.

1. Select an unreadable, malformed or semantically invalid save → show a useful failure message without replacing the active game.

2. Cancel the picker or error dialog → return to a usable prior screen; failed Continue does not invent a new game.

3. Opening a save never rewrites or repairs the file. A failed load must not overwrite it with the current world.

4. After failure, load a valid current-schema save successfully. Missing required identity is rejected; backward save migration remains outside current development.

5. Prepare and validate the complete candidate before stopping the active game. Missing/unreadable files, malformed or empty JSON, missing required data, invalid unit/player references and unsupported campaign/mission identities show the existing localized load-failure dialog. Closing it preserves the prior screen and permits retry; there is no automatic repair or replacement save. A canceled file picker is a no-op.

6. Read failure must not write either the selected source or Continue snapshot. Successful load uses the current schema and ordinary turn-resume behavior. This requirement does not implement recovery-slot rotation or atomic writes; those belong to R-0068. Programming errors in starting an already constructed game remain distinct from data rejection.

## 3. Implementation steps

1. Source inspection selects A04. `GameController.loadModelFromFile` already constructs via `GameModelDao` before replacing the current game, but catches only `IllegalArgumentException`. Extend the file/data rejection boundary to the actual read/parse/missing-data failures without catching startup failures or caller null arguments. Reuse the localized dialog and boolean result followed by the existing Load/Continue navigation.

2. Use real `GameModelPoDao` and existing Guice campaign fixtures in `GameLoadRejectionTest`; this repository's Mockito cannot mock final DAOs. Exercise malformed JSON, unreadable/missing source, required identity/reference and campaign failures, unchanged source bytes, and successful retry. Keep the existing startup-failure and null-caller tests.

3. Add a bounded UI recovery journey using existing file-selection/test helpers: failed Continue without an active game, failed Load with an active game, preserved model identity and file bytes, dismissed feedback, canceled picker and successful retry. Preserve existing TC24/TC39 rejection assertions. Follow the [functional contract](../../functional-tests.md), including named page verification methods and Docker execution.

4. Implementation and checks are recorded in the [functional evidence](../../functional-tests.md#r-0067-load-recovery-2026-10-16). Acceptance complete on 2026-10-16; [full regression and publication evidence](../../functional-tests.md#integrated-acceptance-through-r-0069-2026-10-16) records the verified result.

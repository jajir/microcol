# R-0440 — Open player saves in the map editor

1. Status: done
2. Updated: 2026-11-10
3. Related: UC-001 (SETUP-001); [R-0435](R-0435.md).
4. Dependencies: existing archive validation and scenario draft editor.
5. Primary area: [A03](../areas.md#a03).
6. Related areas: A04 saved-game archive integrity and source preservation.
7. Origin: user requested support after investigation of attached `konec.akropia`.

## 1. Summary

1. Developers need to open a current saved game in the map editor and edit its world.
2. Source inspection on 2026-11-10 at `56ad4604` found that the editor parses ZIP archives as JSON. The supplied save also has a 120 × 80 map, exceeding the editor's 100-tile side limit.
3. Support current save archives alongside plain authored scenarios, without changing normal game loading or save compatibility.

## 2. Behavior

1. With developer mode enabled, both editor Open and the existing developer Load route accept a valid saved-game archive and display its world, units and settlements.
2. Accept map sides from 10 through 120 tiles, including the supplied 120 × 80 world; creation, reopening and validation use the same limit.
3. Imported archives open as independent, initially clean scenario drafts. Save still exports plain scenario JSON, with the default name `scenario.akropia`; the archive is not an implicit save destination. Opening or editing never writes the source file.
4. Existing plain scenario opening, saving and reopening remain unchanged. Cancel or a malformed/unsupported archive keeps the previous draft and reports failure through existing localized feedback.
5. This imports world state for editing; it does not add new gameplay rules or change editor Play semantics.

## 3. Implementation steps

1. Detect ZIP signatures in `GameModelPoDao`; reuse its strict `loadPlayerGame` validation for archives and `loadScenarioFromFile` for plain scenarios. Route both editor entry points through the existing `EditorActions.read` and detach archive source paths from the draft's save target.
2. Raise the shared draft side limit to 120 and preserve bounded validation. Keep package ownership unchanged.
3. Verify signature handling and limits in model/JUnit tests. Extend `TC_210_F241_map_editor_lifecycle_test` to open the supplied archive via both routes, export/reopen the draft, preserve source bytes, and reject a broken archive without losing the draft.
4. Apply the shared Java formatter, review the diff, then run model/JUnit, targeted editor UI/source-contract tests, fixed smoke, documentation consistency and strict MkDocs. Local acceptance passed: 5,117 model/JUnit, 13 targeted editor/source-contract and 21 smoke/support checks, all without failures/errors/skips. Results are in [functional evidence](../../functional-tests.md#r-0440-saved-game-map-editor-import-2026-11-10).

# R-0379 — Land one eligible passenger directly or select several with checkboxes

1. Status: done
2. Updated: 2026-10-31
3. Related: P08; CARGO-008 in the [transport rules](../../gap-analysis.md#transport-ships-and-atlantic-travel); UC-025 (Hra) in [use cases](../../use-cases.md).
4. Dependencies: [R-0022](R-0022.md) passenger eligibility, movement costs and validated transfers; existing [passenger interaction rules](../../ux.md#vylodeni-pasazeru-r-0379).
5. Primary area: [A03](../areas.md#a03).
6. Related areas: A06 owns passenger eligibility and transfer rules; A04 retains saved passenger locations and equipment.
7. Origin: user agreement on 2026-10-31 following discussion of the single-passenger dialog; selected for implementation on 2026-10-31 in the user's ordered list after R-0381.

## 1. Summary

1. A player landing passengers should avoid a redundant choice when only one person can land, and should be able to select several people together when there is a real choice.
2. Source inspection on 2026-10-31 at `62d788e6` found that map landing always opens a radio-button dialog and preselects its first passenger, including when only one passenger is eligible. This follows the historical [R-0022 contract](R-0022.md#2-behavior); it is not new runtime verification.
3. Replace only this map-landing interaction. Passenger eligibility, movement costs, equipment, port arrival, boarding and other cargo operations keep their existing rules. The interaction is implemented and locally accepted; chapter 3 links the verification evidence.

## 2. Behavior

1. The player selects a ship and gives the existing landing command toward an adjacent land tile. Count passengers who can legally land on that particular tile now, not all people aboard. With no eligible passenger, preserve the existing rejection and do not open an empty selection dialog.
2. With exactly one eligible passenger, that passenger immediately lands on the selected tile without a selection or confirmation dialog. This also applies when other people remain aboard but cannot land there. There is no intervening Cancel action.
3. With two or more eligible passengers, open a dialog listing those passengers with independent checkboxes, all unchecked on every opening. The player may select one, several or all; no passenger is selected automatically. Opening or changing the selection does not move anyone.
4. The dialog heading is “Select passengers to disembark” / “Vyberte pasažéry k vylodění” and the action is “Disembark selected” / “Vylodit vybrané”. Confirmation is disabled while nothing is checked, including after the last checkbox is cleared. Checkboxes and actions remain keyboard accessible: Tab moves between them and Space toggles a checkbox or presses the focused action.
5. Confirming lands only the checked passengers on the chosen tile; unchecked passengers stay aboard. For example, with three eligible passengers, checking the first and third lands those two and leaves the second aboard. Cancel or Escape closes the dialog without landing anyone; reopening starts with all checkboxes unchecked.
6. Existing model validation still rejects illegal transfers if the situation changes before confirmation, and the player sees the existing passenger-transfer rejection. Checked passengers land one after another; a rejection leaves that passenger and every later checked passenger aboard, while a transfer completed before it remains valid. Preserve passenger identity, equipment, normal movement costs and the ship's unchanged position; save/continue retains completed transfers under the existing persistence rules.

## 3. Implementation steps

1. Ownership: eligibility and every transfer precondition stay in `AbstractUnit.canUnitDisembarkAt` / `disembarkToLocation` (the [passenger model owner](../../architecture.md#individualni-preprava-pasazeru-r-0022)), which validates before mutation. No model, persistence, AI or save-schema change is needed. Zero eligible passengers keeps the existing `UnitWithCargo.isPossibleToDisembarkAt` branch failing, so the ordinary movement rejection appears as before.
2. `GamePanelPresenter` filters cargo passengers with the model predicate for the target tile. Exactly one lands directly; two or more open `ChoosePassengerDialog`. Its only caller is this presenter.
3. `ChoosePassengerDialog.choose` returns `List<Unit>`: the checked passengers in hold order, empty on Cancel/Escape. Each passenger is a `CheckBox` (`#passenger-choice-<id>`), created unchecked on every opening; `#passenger-heading` shows the new `Dialog.passenger_heading` text and `#passenger-confirm` is disabled while none is checked. English and Czech `passenger_heading`, `passenger_destination` and `passenger_confirm` texts are updated; `passenger_title` remains the rejection-message title.
4. `GameModelController.disembark(List<Unit>, Location)` lands the passengers sequentially on its existing background thread and stops at the first `IllegalStateException`, showing the existing rejection message.
5. Player scenarios in `TC_29_F21_passenger_transfer_test` (F21 fixture; test-local fixture variants add a third colonist or exhaust the pioneer):
   1. `TC_01_select_passengers_cancel_and_continue`: B2.3–B2.5 — two unchecked checkboxes, English heading/action, confirm disabled initially, enabled by one check and disabled again after clearing it, no movement while toggling, Cancel and Escape land nobody, reopening resets, one selected passenger lands, Continue, and the sole remaining passenger lands directly (B2.2).
   2. `TC_02_changed_shore_rejects_confirmation_without_unloading`: B2.6 — both checked, the shore becomes occupied, the model rejects and nobody leaves the ship.
   3. `TC_07_keyboard_lands_first_and_third_of_three_passengers`: B2.4–B2.6 — three eligible, Tab/Space checks first and third, keyboard confirm lands exactly those two, the second stays aboard, and Continue keeps them.
   4. `TC_08_czech_dialog_lands_all_selected_passengers`: B2.4/B2.5 — Czech heading/action, select all, both land with equipment and movement costs; goods hold retained.
   5. `TC_09_sole_eligible_passenger_lands_directly_and_none_is_rejected`: B2.1/B2.2 — the exhausted pioneer stays aboard while the rider lands without a dialog; then nobody is eligible and the ordinary rejection appears without a selection dialog.
   6. `TC_03`–`TC_06` retain port, pier, foreign-ship and full-ship transfer assertions unchanged.
6. Other dialog callers adapted: `TC_01_F01_embark_disembark_test#TC_01_embark_disembark` (second passenger lands directly), `TC_38_F30_coastal_port_movement_test#TC_01_loaded_port_entry_cancel_save_and_return` (passenger starts unchecked), `TC_140_F131_treasure_cargo_test#TC_05_sole_aboard_train_lands_directly_and_unloading_frees_the_holds` (renamed; the sole train lands directly), and all `TC_101_F92_four_nation_expedition_loop_test` expeditions via `ExpeditionLoopPage.disembarkSolePassenger`. `TC_24_F15_free_play_setup_test#TC_12_original_world_river_landing_and_colony_survive_continue` keeps two eligible passengers and its checkbox choice. No model tests are added because no rule logic changes.
7. The implementation is locally accepted, including direct landing, multiple selection, cancellation, keyboard use, stale-state rejection, persistence and readable English/Czech captions. Acceptance follows the [local acceptance policy](../../publishing.md#local-acceptance-policy); actual runs, review and repaired visual evidence belong in the [functional test evidence](../../functional-tests.md#passenger-landing-selection-r-0379-2026-10-31).

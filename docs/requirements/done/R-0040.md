## 2. Behavior

1. A newly captured requirement has status `new` and four chapters: summary,
   behavior, implementation steps and open questions. For gameplay, a reader
   can assess chapters 1 and 2 without knowing the code.
2. Selecting the requirement for development moves it to `waiting for refinement`,
   including active refinement. Complete agreed scope, observable acceptance,
   available dependencies and resolved blockers make it `ready for development`.
   Completed implementation with passing acceptance makes it `done`.
3. Deliberately postponed work is `deferred`; abandoned work is `canceled`.
   Reasons and conditions for return are recorded. Failed checks do not mean done,
   and publication remains separately verified. No seventh lifecycle state is added.
4. A refinement-only request does not start implementation. During authorized
   implementation, status remains `ready for development` with a brief progress
   note; a required behavior decision returns it to refinement.
5. The later migration creates linked new requirements for unimplemented outcomes,
   preserves old decisions/evidence/IDs and explicitly identifies verification-only
   gaps. Further development follows agreement; this change does not migrate them.

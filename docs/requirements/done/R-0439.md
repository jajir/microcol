## 1. Summary
1. Players need more space to inspect and edit their keyboard shortcuts.
2. The current modal limits the list to a small viewport while Settings remains behind it.
3. Replace that modal with a full-page editor inside the main window, reusing the existing shortcut rules.

## 2. Behavior
1. Keyboard shortcuts in either menu or in-game Settings opens the full-page editor. Only its rows scroll; title, explanations, feedback and actions remain visible.
2. Header actions run left to right: Restore defaults, Cancel, Save and back. A larger gap separates reset from the last two actions; saving is emphasized.
3. Reset changes only the draft. Cancel and Escape discard it and return to Settings, preserving its menu/game origin. Save and back persists and activates the draft before returning to Settings.
4. While recording a combination, Escape cancels only that recording, preserves its previous binding and keeps the editor open. Captured keys must not execute game commands. The global Load shortcut cannot leave the editor and discard its draft.
5. Existing conflict rejection, disabled save during capture, failed-save recovery, multiple bindings, unbound actions and platform defaults remain intact. English and Czech controls must remain readable at 1000 × 700 and normal game size.

## 3. Implementation steps
1. Keep ownership in `gui.screen.setting`: replace the modal by `ScreenKeyboardShortcuts`, use the shared screen header and swap content inside Settings so its origin is preserved.
2. Preserve `ShortcutController` validation and persistence. Attach the key capture filter only while the editor is open and remove it on return.
3. Extend `TC_84_F75_framed_settings_test` and `KeyboardShortcutsPage` to verify a single main window, full-size editor, ordered fixed header actions, EN/CS layout, capture Escape, whole-draft cancellation, save, reset, restart and failure recovery. Run all model/JUnit tests, targeted Docker UI scenarios and fixed smoke/support selection; format changed Java and validate documentation.

## 1. Summary

1. The user needs the top-level requirement directory to contain active requirement files, while retaining finished and postponed work for reference.
2. Source observation on 2026-10-15 at `f5371698`: all 103 requirement files share one directory, including 29 `done` and 12 `canceled` records; no record is currently `deferred`.
3. Scope: organize the actual files by status, document future transitions and repair references. Preserve IDs, decisions, historical evidence and all six existing status meanings.

## 2. Behavior

1. Requirements with `new`, `waiting for refinement` or `ready for development` remain directly in `docs/requirements/`. Shared catalogue and workflow pages remain there too.
2. Moving a requirement to `done` also moves its single authoritative file to `docs/requirements/done/`; `deferred` uses `docs/requirements/deferred/`. Canceled requirements use `docs/requirements/canceled/` so they do not appear among active files.
3. Resuming deferred work returns the same file and ID to the active directory with the workflow's appropriate status. A newly authorized reopening of canceled work follows the same location rule. A new outcome after completed work receives a new linked ID.
4. Every move updates incoming and outgoing relative links in the same change. No duplicate requirement or placeholder remains at the old path. Historical commit links stay immutable; current published page URLs follow the new locations.
5. Number allocation checks all status directories. Existing IDs are never reused, and R-0041–R-0049 remain reserved. Empty status directories remain available with a short index linking the common workflow.

## 3. Implementation steps

1. Extend the single [requirement workflow](../README.md) with the status-to-path rule and reverse transitions; link it from project instructions and catalogue navigation.
2. Move the current inactive records without changing their status or scope; rebase relative links in moved files and update incoming references across the repository. Add the status indexes and keep the existing migration map authoritative for historical dispositions.
3. Verify unique IDs, status/path agreement, preservation of the original records apart from links, and target equivalence for relocated links. Run the documented launcher/documentation unit checks and strict MkDocs build, then inspect rendered active and archived pages. No game or Java behavior changes require local UI acceptance.
4. Current result on 2026-10-15: the status-directory workflow and original-file moves are implemented; original content and link destinations pass the direct audit, and the documented checks and rendered review pass.

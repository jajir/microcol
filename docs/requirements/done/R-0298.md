## 1. Summary

1. A player can save, resume and recover a game from a coherent interface instead of having to know the filesystem layout.
2. The main game offers a dropdown session menu alongside its existing colony selector. Main-menu Load and recovery access share one saved-game browser.
3. The change retains atomic writes, recovery cadence and retirement semantics. Cloud synchronization, screenshots and additional rotating checkpoints are outside this change.

## 2. Behavior

1. The [authoritative navigation page](../../save-load-navigation.md) defines the affected journeys. In-game Menu offers return, save, load, quick save/load, mission restart when applicable, settings, main menu and quit. Escape cancels an active map command first; otherwise it opens the menu. Settings returns to the live game when entered there.
2. One browser lists manual files, quick saves and existing recovery points, with a dropdown filter, saved name, timestamp, mission, year, difficulty, player and nation. Missing entries leave an explicit empty view; malformed metadata remains visible and full loading still rejects invalid game data safely.
3. Save creates a new named entry. Names use the existing Unicode whitespace normalization and 64-code-point limit. Filenames are generated independently of player text. Overwrite and delete require explicit confirmation and are available only for manual entries. Import/export preserve access to the operating-system file chooser; opening the save folder supports backups.
4. F5 and the menu write one quick save per playthrough; F9 and the menu restore it through the common replacement guard. Loading a saved playthrough preserves its quick-save identity. Authored scenarios without library metadata receive a new identity in memory and are never rewritten when opened.
5. Replacing a live game, restarting a campaign mission, going to the main menu and closing the application share Save and continue / Leave without saving / Cancel. This first implementation conservatively asks whenever a game is active; it does not infer whether gameplay changed. Saving here replaces the latest-position recovery point. Failure keeps the game and cancels the pending transition; cancellation and Escape do the same.
6. A load is fully reconstructed and validated before the leave guard and activation. A corrupt target never causes the active game to be lost. Continue uses the most recently successfully saved/loaded location; automatic checkpoints also update that location. Manual saves and quick saves cannot overwrite automatic slots through the browser.
7. Ordinary saves/quick actions require the prepared human turn. Existing failed-turn recovery remains available. Restart starts the original campaign mission; free play does not expose mission restart. New free play and mission selection remain separate entry points in the main menu.

2. Reuse the current toolbar's final control for the dropdown and its existing frame/icon. Update menu access, keyboard actions, settings return and window-close cancellation together. Existing external-file test fixtures use the explicit import/export actions.
3. Extend the recovery/load journeys and add a session-menu scenario plus catalogue/model checks. Apply the shared Java formatter, run targeted Docker/Xvfb scenarios, all fast model/JUnit checks, the fixed 360-second smoke gate, documentation consistency and strict MkDocs. Record actual outcomes in [functional tests](../../functional-tests.md), not here. The implementation and required local acceptance are complete; detailed results remain in the linked evidence.

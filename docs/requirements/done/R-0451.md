1. Status: done
2. Updated: 2026-11-10
3. Related: UC-031/033/114/119, colony work and feedback; [use cases](../../use-cases.md).

## 1. Summary

1. Players need to understand why a worker cannot be moved to another colony field after spending movement points.
2. Source inspection on 2026-11-10 at `110e3f51` found a shared rejected-drop dialog, but insufficient movement was reported as a generic unavailable worker or square.
3. Explain this rejection before and after release without changing movement costs, work rules or saved data.

## 2. Behavior

1. In colony detail, drag a worker over an otherwise available field that cannot be reached with the remaining movement. The status bar explains that the worker does not have enough movement points for this move.
2. Releasing over that field opens a modal explanation with OK; either OK or Esc closes it. Hovering alone never opens the dialog.
3. Rejection preserves the worker's location, assigned work, remaining movement, equipment and colony state. Canceling the drag or leaving the target clears the transient movement hint; closing the dialog does not restore it.
4. Cover both zero movement and an insufficient fractional remainder. A legal transfer remains legal, including existing same-location and full-allowance rules. Other rejection reasons retain their current messages. English and Czech text use the existing localization mechanism.

## 3. Implementation steps

1. Distinguish insufficient allowance inside the existing model transfer-cost calculation and expose a read-only ColonyField query that checks other assignment preconditions first.
2. Reuse PanelColonyFields hover/drop handling and DialogMessage with its existing OK/Esc behavior. Clear the transient movement hint on drag exit, completion and cancellation.
3. Extend SharedColonyFieldAssignmentTest and TC_39_F31_shared_colony_fields_test/TC_10, preserving fixture, linear player steps and page verification methods. Run all model/JUnit checks, targeted TC39, TC51 and native-land TC114/05 plus PageVerificationContractTest in Docker/Xvfb, then fixed smoke/support. Apply shared Java formatting and run documentation consistency, naming audit and strict MkDocs.
4. Implemented and locally accepted: 5,119 model/JUnit, 16 targeted UI/source-contract and 21 smoke/support tests passed, all without failures, errors or skips. Shared formatter, documentation consistency and strict MkDocs passed. See [functional evidence](../../functional-tests.md#r-0451-worker-movement-feedback-2026-11-10); full regression and publication remain separate.

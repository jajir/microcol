# R-0317 — Explain local Docker preparation timeouts

1. Status: done
2. Updated: 2026-10-27
3. Related: developer verification infrastructure; no gameplay UC.
4. Dependencies: [local test lock](R-0292.md), [completion runner](../../ai/completion-callbacks.md) and [local acceptance](../../publishing.md#local-acceptance-policy).
5. Primary area: [A01](../areas.md#a01), project infrastructure supporting application delivery.
6. Related areas: none; no game-layer responsibilities change.
7. Origin: the user approved minimal diagnostic logging after analysis of recurring 20-second Docker preparation timeouts.

## 1. Summary

1. Developers need to distinguish a stalled Docker preparation command from a test deadline and queue waiting, and retain enough evidence to investigate the next occurrence.
2. Analysis on 2026-10-27 found 13 local runs from 26–27 October that timed out in the initial Docker container query before a test command started. Their existing evidence identifies the command and deadline, but not the cause of the delay.
3. Extend the current runner's evidence and notification. Preserve execution limits, cleanup ownership, acceptance rules and historical results.

## 2. Behavior

1. A local verification request records queue waiting, preparation commands, execution and cleanup with timestamps, elapsed time, limits and outcomes in its existing log.
2. A timed-out Docker preparation or cleanup command records partial output and triggers short, read-only diagnostics within the remaining job budget. A successful diagnostic probe never makes the original run successful or starts/retries tests.
3. The diagnostic captures selected client/context and host-load information, Docker process state and server availability. Only a responsive server permits a diagnostic repeat of the container query. Each probe and the collection have bounded time limits. Diagnostic failure preserves the original failure.
4. Notifications identify the failed phase and say when the test command never started. Existing result status values remain compatible. Credentials, full environment/configuration contents and unrelated process listings are not collected.

## 3. Implementation steps

1. Extend `scripts/ui-tests/local_slot.py` with timed command events and bounded diagnostics; reuse `command.log` and existing lock/recovery ownership.
2. Pass the existing job budget from the completion runner and direct budgeted entry point. Add phase and command-started metadata to local completion results and notifications; leave worker and CI execution unchanged.
3. Test partial output, probe budgets, original-failure preservation, absence of test retries, private-data filtering and notification content. Run affected tooling tests, all model/JUnit checks, fixed smoke/support and documentation checks. No player behavior changes require additional targeted gameplay scenarios.
4. Keep operating details and actual acceptance results in the [completion-runner documentation](../../ai/completion-callbacks.md#timeout-evidence-2026-10-27). Distinguish observed delays from verified logging behavior; one captured cause does not establish the cause of every historical stall.

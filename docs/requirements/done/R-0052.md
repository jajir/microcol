# R-0052 — Process each national turn once in the agreed order

1. Status: done
2. Updated: 2026-10-15
3. Related: P03; TURN-001/002; UC-005 (Hra). See the [rules](../../gap-analysis.md), [use cases](../../use-cases.md) and [work packages](../../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: Existing participant identities, owner-turn boundary and save/load; order only currently available phases, without requiring new native or market systems.
5. Primary area: [A04](../areas.md#a04).
6. Related areas: A06 Europe events/arrivals; A07 colony updates; A10 pending political decisions.
7. Origin: [R-0002](../canceled/R-0002.md). Unfinished original outcome under the [migration](../migration-2026-10-14.md).

## 1. Summary

1. The player needs Europe events, colony processing and unit actions to occur once per national turn in a predictable order, including after Continue.
2. Baseline observation on 2026-10-15: `GameManager` follows the player-store list, which appends Crowns after non-Crowns. `Player.startTurn` processes units, colonies, then scheduled human immigrants. Loading already avoids calling that method, but the complete order and save-boundary acceptance are missing.
3. Scope: order existing actors and update stages under [national turn processing](../../gap-analysis.md#national-turn-processing). Preserve existing colony/voyage accounting and campaign objectives. Native systems, new tax/market events and political decision dialogs remain with their own requirements.

## 2. Behavior

Agreed on 2026-10-15 under the authorized implementation run; implementation and acceptance are recorded in chapter 3.

1. For participants present, use natives, England, France, Spain, Netherlands; other scripted participants follow in stable identity order. Then process Crowns in their associated nation's order. Absent actors require no dummy turn. Changing the human selection, display name or serialized player order does not alter the sequence.
2. Each actor's preparation processes existing voyages and scheduled Europe immigration, then its colonies, then movement replenishment and continuing unit work. Only after all stages finish can that actor move, fight or manage. Each existing stage runs exactly once; later systems must join their documented stage without restarting earlier work.
3. Save before ending an actor's turn, Continue and end it → the next actor is prepared once. Save after that preparation, Continue repeatedly → stocks, population, voyage countdown, work countdown, movement, date and active actor are unchanged. Preparation itself is not a save boundary; a partial snapshot must be refused before any save file is replaced. Opening an existing save does not rewrite that file.
4. One full round, including present Crowns, advances the shared calendar exactly once. A new game starts with the first present actor; a loaded game resumes its saved actor. No calendar advance occurs from opening screens, reports or Continue.
5. A pioneer improvement completed during unit activation affects the following colony update. Preserve the current colony update's food, birth, famine and queue rules; their remaining acceptance and rule changes belong to R-0057–R-0059 and other owning requirements.
6. If preparation fails, keep the instance unavailable for actions and saving. Returning to the menu leaves existing save files unchanged, explains the failure, and offers the existing Continue/load route. Keep Exit available during turn preparation; movement retains its existing button restrictions.
7. The turn-start notification and human-turn recovery save occur after preparation. Available pending political systems retain their own state; adding future tax or Congress decisions must not replay an already completed update. This requirement does not claim those currently absent systems work.

## 3. Implementation steps

1. `GameManager` owns a stable turn sequence built from a fresh copy of the registered actors at each transition, without reordering the shared player list. Validate the current actor remains the registered identical object before finish notifications or mutation; do not retain a stale cached roster. Use existing internal nation keys (`England`, `France`, `Spain`, `Dutch`), never editable display names; Crown ordering follows `PlayerKing.getWhosKingThisPlayerIs`, not its name. Other scenario identities get a deterministic identity tie-breaker. Keep native-first placement in the shared contract for the future native actor owner; no native dummy or new native AI is required. Preserve the stored current actor when loading.
2. `Player.startTurn` owns the three synchronous preparation stages. Separate voyage advancement from ship movement replenishment so it runs before colonies and never twice. Retain scheduled immigration's existing eligibility and trigger. Refresh surviving/new units only after colony processing. Keep colony accounting in `Colony`, voyage rules in `Ship`, and unit work in its existing action owner; UI/AI receive the finished turn event.
3. Serialize model snapshot creation against start/end-turn transitions and reject reentrant snapshots during preparation. The existing started/current-actor state represents the completed action boundary; no intermediate-phase save schema or migration is needed. A failed preparation must not become a valid actionable/save boundary. Validate turn entry before mutation and keep model action preconditions unavailable during preparation. The existing `GamePanelController` input gate reads model running/current-actor state; that shared readiness must also prevent input during preparation, independently of notification order. Preserve the controller/DAO order that creates a model snapshot before opening the output file. R-0051 restricts `TurnStartedListener` recovery writes to fresh human turns. Preserve that guard and ensure those events follow completed preparation; retain the separate menu-position recovery behavior. A resumed notification must not repeat rule work or overwrite the opened save.
4. Add `NationalTurnOrderTest` for shuffled actors, absent nations, named/scripted actors, Crown association, fresh start, loaded current actor and one calendar advance. Add preparation/continuation tests covering real production, birth, arrivals, pioneer countdown and movement, including repeat Continue and attempted save/action during a preparation callback. Use current-schema fixtures and actual save/load, not only mocked call counts.
5. Allocate `TC_36_F28_national_turn_order_test` and `F28-national-turn-order.microcol` for a real multi-actor round and save/Continue journey. Keep linear player steps and page-object `verify...` assertions. Reuse the existing navigation, colony, Europe and calendar controls. Preserve TC_21's Continue journey and the voyage/food/pioneer scenarios; update fixture expectations only where the agreed order changes an observable outcome.
6. Caller acceptance: shared Java formatter, model boundaries, `PageVerificationContractTest`, targeted TC_36/TC_21/voyage/food/pioneer cases in Docker Xvfb/Openbox, then the full documented regression. Update architecture/package responsibility text if the ownership description changes, rule/UC evidence and functional results. Publish through main and verify actual delivery. The agreed scope is complete: the preparation boundary and GUI recovery passed full regression and publication checks.

7. Partial delivery on 2026-10-15: deterministic actor ordering, current-actor identity validation, voyage/immigration → colony → unit-work staging, and real save/Continue coverage. See [acceptance evidence](../../functional-tests.md#r-0052-partial-turn-order-delivery-2026-10-15). This publication does not close the requirement. The subsequent boundary delivery adds synchronized snapshots/transitions, command guards, internal work completion, and recovery through the menu. See [boundary acceptance](../../functional-tests.md#r-0052-preparation-boundary-2026-10-15).

8. Completed on 2026-10-15 after the [full acceptance and publication](../../functional-tests.md#r-0052-preparation-boundary-2026-10-15). The earlier partial delivery remains historical evidence; native actors and new market/tax systems retain their own requirements.

## 1. Summary

1. The player needs to choose useful work using the selected worker’s actual opportunities, without discovering hidden moves after confirming.

2. Current situation: The shared job picker and model-owned current/best yield previews are implemented, verified and published as `dev-107-75341b36bcc2`. See the [acceptance evidence](../../functional-tests.md#r-0056-job-choice-implementation-2026-10-16).

3. Scope: the ordinary-worker choice and previews below, including the supported master blacksmith. Preparation follows the user’s implementation request; the wider specialist roster stays in R-0074. The R-0055 prerequisite is verified and published; refinement is complete and implementation is authorized.

## 2. Behavior

Agreed behavior on 2026-10-16; the authoritative [job-choice rules](../../gap-analysis.md#colony-job-choices-and-yield-previews) resolve the supported-job and yield-label questions. The prerequisite and the implemented model/UI contract below are verified.

1. Open a worker’s work choice from an occupied field, indoor job or colonist at the colony center → show supported outdoor and producing indoor jobs with localized names. A field worker sees current-field and best eligible yields; an indoor or center worker sees the best eligible outdoor yield. Mark the master blacksmith’s tools specialty. Unavailable jobs show a reason, not a fictional output.

2. Choose outdoor work from an indoor job or the colony center → use the best eligible field for that worker and commodity. Exclude occupied/shared/invalid fields. Equal best yields use the existing stable field order; never occupy another worker’s square.

3. Change crop for a worker already on a field → keep that field. Provide an explicit move-to-best action showing destination and yield for deliberate reassignment. The worker’s own field is eligible when comparing yields; choosing it again does not duplicate the worker.

4. Opening, browsing or canceling changes nothing. If the worker’s original job, chosen field/slot, ownership or turn becomes invalid, or the shown potential output changes before confirmation, leave assignments, equipment and stocks unchanged, explain rejection and refresh choices. Do not silently redirect a stale confirmed choice to another destination.

5. Job previews and assignment reuse the [shared-square rules](../../gap-analysis.md#shared-colony-working-squares), including global occupation and rejection of contradictory saved jobs. The resolved persistence policy is not a new open question.

6. Indoor choices show the worker’s potential per-turn output, the needed input and current stock, with a shortage warning. They do not present that potential as guaranteed warehouse growth or include the building’s automatic base production. Example: 3 tools potential, 3 ore required, 1 ore currently available must clearly show the shortage. Expert previews use the same multiplier as actual production.

7. Preserve manual job dragging and ordinary crop changes. Offer supported jobs only in existing producing buildings, keep their slot limits and preserve last-resident moves within the same colony. Non-producing buildings and teaching are separate features. Invalid equipment returns must fail before an old job or warehouse changes.

## 3. Implementation steps

1. Source review on 2026-10-16 found local crop previews in `PanelColonyFields` and slot dragging in `AbstractPanelConstructionWithSlots`. `ColonyField` provides shared-square admission; `ConstructionSlot`/`Construction` own indoor output, inputs and expert modifiers. Keep previews and assignment validation in `model`, with UI presentation in `gui.screen.colony`, following the [package map](../../architecture.md). A preview must not move a unit temporarily or mutate/save/reload the live model to estimate output.

2. Provide the read-only job preview and confirmation contract below that retains the original worker/place and proposed destination. Share outdoor yield computation with `ColonyField.getProduction` and indoor potential/input computation with `ConstructionSlot`; do not add independent UI formulas. Extend the existing indoor placement boundary where needed so the menu and drag path enforce the same owner, identity, turn, source, capacity and equipment rules before mutation. Preserve the no-food-field founding path, which registers the colony before assigning its founder to the Town Hall. Saved-job restoration uses separate constructors/setters and must not acquire live-turn admission checks. Current-schema persistence should need no new stored menu state.

3. Acceptance must compare one worker across two free fields with different yields and a better occupied/shared field; test current-field crop preservation, explicit relocation, ties, no eligible field, indoor-to-outdoor choice, expert marking, indoor shortage labels, cancellation and stale worker/destination rejection. Compare previews with actual output for isolated workers with sufficient inputs and with known shortages, separating worker output from base production and consumption. Extend model tests and ordinary colony UI journeys under the [functional contract](../../functional-tests.md); use the reserved `TC_40_F32_colony_job_choices_test` and `F32-colony-job-choices.microcol` IDs (checked unused on 2026-10-16). The prepared fixture design uses prairie/current lumber 1, free tundra 2 and grassland 3, and a shared occupied desert 6; a master blacksmith has 1 ore against the 3-ore input need. The preparation-only runtime check passed loading, exact save/load round-trip and read-only yield/admission queries: the master produces 6 tools with 3 ore or 2 tools with the available 1 ore. See [fixture evidence](../../functional-tests.md#r-0056-fixture-preparation-2026-10-16); these checks do not verify the future picker.

4. Current result: shared admission, immutable choices, worker-aware yields and all three picker entry points are complete. All 15 TC40 player scenarios, the full 1298-game/185-UI regression, three native packages and Java compatibility pass. Stale menu and drag choices reject atomically and refresh without automatic assignment. Published as `dev-107-75341b36bcc2` from `75341b36`; see the [acceptance evidence](../../functional-tests.md#r-0056-job-choice-implementation-2026-10-16). This closes the scoped requirement and UC-033; additional specialist types remain in R-0074.

5. Reuse the colony's `AbstractMessageWindow` pattern for one job picker, opened from worker context controls in `PanelColonyFields`, `AbstractPanelConstructionWithSlots` and `PanelOutsideColonyUnit`. Keep the field's existing crop actions and the center worker's equipment actions; add the shared work-choice entry without replacing them. The picker shows current/best outdoor output and indoor potential/input details, keeps selection as a draft, and has explicit confirm/cancel controls. Use localized commodity/building names, wrapping labels, keyboard selection, Enter to confirm and Escape to cancel. Preserve the center worker's Context Menu/Shift+F10 entry. After rejection, display the reason and rebuild choices without executing a replacement choice; after success, repaint the colony using the existing event.

6. Source review found that indoor dragging currently admits a drop without checking worker eligibility and calls the placement command through two target-selection paths. Both paths must use the shared slot query, then recheck the same selected slot at drop and handle expected rejection by reopening the existing picker with an explanation and refreshed choices. Do not automatically execute a replacement job. Do not put live admission in `ConstructionSlot.set`, which also restores saved assignments. Freeze the original `Place` identity and outdoor crop in each offered model choice: the crop can change while the `Place` object remains the same. A current-job choice is a validated no-op; another newly available field or slot cannot substitute for a stale confirmed destination. Keep these checks in model code, outside labels and event handlers.


7. `Colony.getJobChoices(Unit)` supplies an immutable list of model-owned `ColonyJobChoice` values. Each value represents one explicit action: keep/change the current field, move to the shown best field, or occupy the shown indoor slot. Carry current/best outdoor yields where relevant, indoor potential/input/current-stock values, the specialty marker and a model reason for an unavailable action. Enumerate outdoor goods in existing goods order from the local terrain's supported production, including occupied fields when determining which jobs exist; occupation affects eligibility, not whether the job vanishes. Use existing field order for ties and existing construction/slot order indoors. The worker's own job remains eligible for a validated no-op. The UI presents these values and confirms the exact choice; it never searches for a replacement destination.

8. Keep choice creation and confirmation read-only until all checks pass. Capture worker/colony/model identity, original place and crop, exact target and displayed potential output; at confirmation recheck identity, source, turn, target eligibility and output before calling existing placement/crop operations. A changed potential output requires refreshing the offer. Indoor input stock is advisory because assignment does not consume it and future production is not guaranteed; ordinary stock changes alone do not invalidate an otherwise legal assignment. Share worker-aware outdoor potential with actual `ColonyField` production and indoor potential with `ConstructionSlot` production. Keep the existing shortage calculation, equipment operations and save schema; no preview may temporarily assign a worker.

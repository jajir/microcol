## 1. Summary

1. The player needs safe job changes when two colonies share a working square, without losing a worker or counting its output twice.

2. Current situation: Live assignment checks, UI admission, saved-assignment validation and the role/identity/turn/direction/equipment boundary matrix are implemented, verified and published as `dev-105-3c521c5dcb9a`. See the [verification evidence](../../functional-tests.md#r-0055-completion-work-2026-10-16).

3. Scope: safe outdoor assignment, crop changes and restoration of those assignments. Selection and refinement on 2026-10-16 retain the delivered founding rules; building capacity, fortified-colony minimum residents (R-0082) and the general jobs menu (R-0056) remain separate outcomes.

## 2. Behavior

Agreed acceptance on 2026-10-16 under the user’s authorization to choose reasonable answers; the authoritative [shared-square rules](../../gap-analysis.md#shared-colony-working-squares) own this contract.

1. Colonies at (10,10) and (12,10) share (11,10). If one works that square, the other cannot place a second worker there, including across different owners.

2. Vacate the square → a valid worker may take it. Changing crop on the same square creates no second worker or second production contribution.

3. Invalid crop, stale occupied target, missing colony or invalid ownership → preserve the old job, equipment and both colonies’ stocks.

4. Moving the last resident between jobs in the same colony preserves the colony. Canceling a drag changes nothing; save/load preserves globally unique assignments.

5. Only a registered colonist belonging to the colony’s owner may take an outdoor job during that owner’s prepared turn. The worker must already work inside that colony or stand at its center; workers from another colony must first travel there. A map unit’s equipment is returned only if every returned item fits. Invalid role, stale identity, wrong owner/turn, distant location or stopped game leaves the whole operation unchanged.

6. The colony field display prevents a drop on a globally occupied square and explains its unavailability. If the state changes after a drag or crop menu opens, recheck on confirmation, keep the worker and stocks intact and show an understandable rejection. Opening or canceling the controls changes nothing.

7. Loading rejects contradictory field assignments before replacing the current game: two workers on one world square, one worker referenced by multiple jobs, a missing/wrong-owner worker, or a worker whose saved place disagrees with its field. Do not relocate workers, silently drop assignments or rewrite the source file. A valid saved game keeps worker identities, crops and one production contribution per square. Load and Continue explain invalid saved assignments and stay on the current screen with the previous game unchanged.

## 3. Implementation steps

1. `model` owns the assignment contract. Reuse `Model.isColonyFieldAvailable` for the global square check used by founding. Expose a read-only eligibility query for the UI and recheck in `AbstractUnit.validateColonyField` before `UnitFreeColonist` returns equipment or detaches the old place. Keep invalid-crop rejection before mutation and retain the existing all-equipment capacity preflight. Same-colony last-resident moves continue to use `destroySimple`.

2. Keep persistence validation independent of live-turn admission: `Model.make` inspects saved field references before `PlaceBuilderPo` can select only the first matching reference. Validate global square uniqueness, unique job references, worker identity/owner and matching saved place. `GameController.loadModelFromFile` already constructs the incoming game before replacing the active one; preserve that ordering and verify failure leaves the source file unchanged. The load controller reports success/failure; both file loading and Continue enter the game screen only after success, using existing localized feedback for rejected input. Catch validation rejection around construction of the incoming game, before replacing the current instance.

3. `PanelColonyFields` uses the model query for drag admission and the model command at drop. Recheck crop changes on the current field. Reuse existing feedback/localization and colony controls; do not implement R-0056’s general jobs menu. UI contains no copy of occupation or inventory arithmetic. Follow the [package responsibility map](../../architecture.md), [UX guidelines](../../ux.md) and [functional test contract](../../functional-tests.md).

# R-0035 — Give the local worker sufficient output and enforce its task contract

1. Status: Implemented; local verification and mixed replay outcomes recorded
2. Updated: 2026-10-14
3. Related: [P31](../implementation-plan.md#seznam-pracovnich-baliku), [R-0034](R-0034.md), [worker operations](../ai/local-qwen.md).
4. Primary area: [A03](areas.md#a03), shared development and verification support.
5. Cross-area dependencies: none; no gameplay or Java package changes.

## 1. Summary

1. The user authorized increasing the current GPT-OSS worker's output/time
   allowances, enforcing text-only execution and preventing repeated caller
   setup/application errors. Keep medium reasoning and existing coding criteria.
2. Historical runs show truncated/empty output at 4096 tokens, unnecessary
   repository reads despite explicit instructions and caller mistakes. A replay
   must distinguish generated code from accepted code and caller repairs.

## 2. Behavior

1. Keep GPT-OSS 20B and context 32768; allow 16384 generated tokens, 1800 seconds
   per attempt and 3600 seconds per task, with at most two targeted repairs.
   Serialize inference and unload before heavy verification. These are approved
   settings, not evidence of improved quality.
2. One repository launcher owns preflight, command construction, cumulative
   budgets, process cleanup and evidence. Reuse the current host-wide lock and
   isolated worktrees. Never reset a task budget through a retry directory.
3. Text-only tasks have command execution disabled and a read-only sandbox.
   Direct editing remains available when deliberately selected. Missing context
   returns to the caller; neither mode silently selects a cloud model.
4. Validate the complete replacement batch, allowed paths, unchanged source
   and exact anchors before applying any edit. The caller retains source anchors;
   new tasks request replacement IDs and new text only. Legacy output is accepted
   only when it exactly identifies those same anchors, enabling original-prompt
   replay. Formatting and tests follow successful application, never a rejection.
5. Replay a previously failed coding prompt with its original acceptance checks
   in isolation. Record limits, model identity, output length, tool calls, time,
   repairs and actual test results. Do not integrate replayed gameplay code or
   present a small replay as a benchmark or token-saving measurement.

## 3. Implementation steps

1. Add a small standard-library launcher and behavioral tests for rejected
   inputs, budgets, tool restrictions, process cleanup and batch application.
   Keep model parameters in the existing Modelfile and other operating values
   in one launcher profile; no per-job copies of limit constants.
2. Update the existing skill/contract and operating page, preserving dated
   evidence. Recreate the local alias from installed weights and verify it.
3. Run isolated replay acceptance, launcher tests, skill validation, documentation
   tests and strict MkDocs. Review and publish through the authorized main flow.

4. Verified on 2026-10-14: the alias exposes context 32768/output 16384; the
   launcher passed 14 behavioral checks, nine documentation checks, skill
   validation and strict MkDocs. The relation-helper replay passed its original
   eight model and three structural cases without manual code repair; the
   attack-role replay exhausted two repairs and failed compilation. Both
   outcomes, timings and limits are in the [operating evidence](../ai/local-qwen.md#larger-output-and-shared-launcher-verification-2026-10-14).
   No replayed gameplay source was integrated.

## 4. Open questions

1. The successful replay stayed below the old output ceiling. The independent
   effect of the larger allowance and long-term reliability remain unmeasured;
   the mixed two-task result does not justify a savings or general quality claim.

# R-0018 — Keep automatic saving and verify Continue

1. Status: Refining
2. Updated: 2026-10-13
3. Related: P26; SUPPORT-001; UC-113/UC-115 (Hra). See the [rule catalogue](../gap-analysis.md),
   [use cases](../use-cases.md) and [work packages](../implementation-plan.md#seznam-pracovnich-baliku).
4. Dependencies: Existing save/load; [R-0002](R-0002.md) phase contract; [R-0014](R-0014.md) profile fields.
5. Primary area: [A04](areas.md#a04).
6. Related areas: A01 Continue/Load and replacement; all implemented state owners.

## 1. Summary

1. Agreed 2026-10-13: keep the current automatic save/Continue option; do not introduce a replacement save UI or new slot design.

2. The user expects saving when returning to the main menu. Source inspection finds writing in TurnStartedListener at human-turn start, while ExitGameListener shows the menu and stops the game without an explicit write. A UI round-trip must establish the actual effect.

3. Two gaps are now distinguished: a fresh application without an initial autosave keeps Continue disabled after saving; a profile with an existing autosave can Continue, but menu entry does not write subsequent movement. The menu presenter refreshes at initialization/game finish, not ordinary menu return. Audit both profiles explicitly.

## 2. Behavior

1. Desired retained workflow: the player makes a move, returns to the main menu, and Continue restores that latest position without a new chooser or prompt.

2. Audit the actual snapshot: begin a human turn, record the automatic save, move a known ship through the UI, return to menu and compare the file. Continue must be checked against the moved ship’s location, not just a successfully opened map.

3. Do not rewrite player saves during this test; use isolated fixture homes. Keep explicit load and automatic turn saves intact.

4. Broader corrupt-file handling, atomic disk writes and additional autosave slots remain separate work; this limited audit does not certify them.

## 3. Implementation steps

1. TC21/TC_05 uses a clean test home without autosave at startup to observe the disabled Continue button after the first save. TC23/TC_02 starts with an explicit fixture autosave, moves the ship, returns to menu and restores the prior position. Neither test may depend on ignored files in a developer checkout.

2. If the expected menu save is missing, keep that as a concrete R-0018 implementation gap. Reuse the existing persistence service for a later fix rather than adding a new system.

3. Re-run continuation after a future timing fix with the latest-position expectation; a baseline observation of lost movement must never be presented as acceptance of the intended behavior.

4. Verification on 2026-10-13: TC21/TC_05 and TC23/TC_02 passed in the targeted run. The clean profile keeps Continue disabled; the pre-existing-save profile restores the ship before its departure. Menu-entry bytes remain unchanged. Full native evidence is tracked in the [functional audit](../functional-tests.md#free-play-audit-2026-10-13).

## 4. Open questions

1. Resolved 2026-10-13: retain the existing save option and menu workflow. The immediate issue is verifying its actual timing; do not ask for a new phase/slot design.

2. No new recovery-dialog decision is needed for the present audit. Invalid-file recovery remains unverified and outside this slice.

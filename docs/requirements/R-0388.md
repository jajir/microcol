2. Updated: 2026-11-01
3. Related: SUPPORT-001; UC-113 (Hra); [save policy](../save-load-navigation.md#pravidla-ukladani-schvalena-1-listopadu-2026).
4. Dependencies: [R-0068](done/R-0068.md) safe turn checkpoints and atomic saving; [R-0298](done/R-0298.md) saved-game management; [R-0387](R-0387.md) accepted save/exit policy.
5. Primary area: [A04](areas.md#a04).
6. Related areas: A01 load/Continue navigation; A03 feedback and [R-0383](R-0383.md) load list; [R-0382](R-0382.md) portable save envelope and metadata.

## 1. Summary

1. Preserve recent turns automatically so the player can recover from a crash or return to an earlier decision without manually creating a save each turn.
2. Existing checkpoints retain latest-turn and decade recovery under R-0068. Per-turn rolling history is requested; the five-save limit and detailed behavior below are recommendations awaiting acceptance, not verified runtime behavior.
3. Scope: bounded history per playthrough using existing saving and loading. No timer, per-unit-action saves, cloud sync, branch manager or configurable retention slider in the initial implementation.

## 2. Behavior

1. When autosave is enabled, create a snapshot once each new human turn is fully prepared, after intervening AI/world processing and before player actions. The initial ready state also creates a snapshot and counts toward the limit. Never capture a partially processed turn or an unresolved mandatory transition.
2. Recommend keeping the five most recent successful turn snapshots per playthrough. With turns 1–5 saved, successfully saving turn 6 removes turn 1 and retains 2–6. Five is a starting policy, not a measured optimum. Turning autosave off stops new automatic writes and rotation without deleting existing saves; re-enabling resumes at the next safe new-turn boundary without backfilling missed turns.
3. Keep each playthrough's history independent. A new game never consumes another game's slots. Preserve the separate decade checkpoint, quick save, manual saves and latest-position exit recovery outside this five-save budget. Autosave never overwrites those categories. All automatic files together are therefore not limited to five, and total storage grows with the number of playthroughs.
4. Loading or merely inspecting an existing save creates no autosave, does not rotate history and never rewrites the loaded file. Loading an older turn retains the same playthrough identity. Subsequent newly reached turn boundaries append to the same history; order rotation by successful save sequence, not the displayed game year. Previously reached later turns remain until they become the oldest retained writes. Equal turn/year labels on different histories are allowed and distinguished by save time.
5. Complete and safely commit the new snapshot before deleting the oldest. A failed write retains all prior recovery files, reports failure visibly and leaves gameplay unsaved. Do not announce success or advance Continue on failure. Cleanup failure may temporarily retain more than five files; report it and retry cleanup on a later successful autosave, never delete a valid recent save to enforce the cap blindly. An interrupted write must not expose a partial file as a loadable save.
6. A successful autosave briefly reports the saved turn/year without a confirmation dialog and becomes the Continue destination. With no subsequent gameplay changes, leaving needs no save prompt under R-0387. Failure keeps the game playable and allows manual/quick-save attempts; the player must not assume automatic protection succeeded.
7. The existing load browser shows each retained snapshot as an automatic save with its actual game turn/year and real save time, newest write first. Reuse current filters and available metadata; never promise a preview before R-0382/R-0383 implement it. Loading applies the same validation and unsaved-progress protection as other saves.
8. Explicitly leaving without saving does not delete existing autosaves. Long turns can still lose actions since the latest snapshot in a crash; quick/manual saves provide mid-turn protection. To preserve an older point beyond automatic rotation, load it and create a named manual save through existing controls.

## 3. Implementation steps

1. Refine after acceptance and selection for development, following the [package map](../architecture.md). Extend existing campaign persistence/checkpoint ownership and the shared browser rather than adding a second saving system. Preserve model/store validation and R-0382's game-data-to-JSON contract.
2. Use playthrough identity and unique managed snapshot identities under its save directory. Record reliable write ordering independent of game date; define restart-safe ordering and post-write cleanup during refinement. Review Continue references, deleted/unavailable saves, initial state, reloaded earlier turns, duplicate callbacks and write/cleanup failures. Reuse atomic file replacement; only managed turn autosaves qualify for rotation.
3. Plan service tests for 0/1/5/6 saves, separate playthroughs, repeated callbacks, reload without writes, replayed turns, autosave off/on, write failure and interrupted cleanup. Extend `TC_43_F34_recovery_points_test` for history and dates, `TC_42_F34_load_recovery_test` for recovery failures, and `TC_191_F224_session_menu_test` for Continue, saved/unsaved exits and quick/manual independence. Preserve stable scenario IDs and the [functional test contract](../functional-tests.md).
4. Current result: documented recommendation only. Implementation requires model/JUnit, targeted Docker UI and smoke acceptance. Documentation-only preparation requires consistency checks and strict MkDocs; it is not runtime evidence.

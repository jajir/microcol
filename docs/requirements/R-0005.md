# R-0005 — Assign a colony worker to a shared map field safely

- Status: Draft
- Updated: 2026-10-12
- Related: P10/P11; COL-002/003/004;
  [UC-032, Hra](../use-cases.md#kolonie-obyvatele-a-vyroba), field occupancy and transfer.
- Dependencies: existing colony/unit identities; no change to colony spacing.

## 1. Summary

A world square may have one working colonist even when it lies in two colonies'
radii. Assignments must either succeed completely or preserve the original job.

Static source inspection on 2026-10-12 at
[`4b3a1b56`](https://github.com/jajir/microcol/commit/4b3a1b567bd9e8c8ad8af1587d9849ecee02bead);
no new gameplay test was run while preparing this draft.
[AbstractUnit.placeToColonyField](../../microcol-game/src/main/java/org/microcol/model/AbstractUnit.java)
and [PanelColonyFields](../../microcol-game/src/main/java/org/microcol/gui/screen/colony/PanelColonyFields.java)
check the local colony field, not another colony's occupation of the same world
square. The model destroys the old place before
[PlaceColonyField](../../microcol-game/src/main/java/org/microcol/model/PlaceColonyField.java)
validates the requested crop: static inspection identifies a rejection-after-mutation
risk, not a newly executed reproduction.

Scope includes global field availability and atomic assignment through existing
manual, founding and capture paths. School rules and a general job-system redesign
remain outside it.

## 2. Behavior

The model provides field availability to the UI and validates the live source,
destination, ownership, crop and occupancy before moving the worker.
The same rules apply to human and AI callers.

Acceptance examples:

- Colonies A at (10,10) and B at (12,10) share (11,10). A works that square →
  B cannot assign another worker there; rejection preserves both jobs and yields.
- A vacates it → B may assign one worker. Changing that worker's crop produces
  one commodity from the same square, not an extra worker or output.
- An invalid crop or stale occupied/removed target → no worker is detached,
  duplicated or moved to a fallback job.
- Moving the last resident between two jobs inside its own colony → the colony
  survives with the same identity and one resident.
- Cancel a drag → assignments remain unchanged. Save/load preserves unique
  occupation of the shared square.

Existing ordinary manufacturing slot limits remain protected; this slice does
not claim acceptance of every COL-004 building.

## 3. Implementation steps

1. Put availability and complete precondition checks in `model`, reusing
   `ColonyField`, `PlaceColonyField` and existing unit placement operations.
   Review all assignment callers, including founding/capture food placement.
2. Make the UI consume that availability and handle a stale result safely;
   check field and building drag paths and moves of the final resident.
3. Validate restored assignments against the same occupancy rule before exposing
   a loaded world. Use current-schema fixtures; do not add save migrations.
4. Add proposed `TC_23_F17_shared_field_assignment_test` and F17 two-colony
   fixture. Retain TC02 and extend `ColonyTest`/`ColonyFieldTest` or focused
   placement tests with rejected-command state assertions.
5. Run model assignment tests and the full functional suite for shared colony
   controls using the [test contract](../functional-tests.md#spousteni-a-ochrana-publikace).
   Verify the same path is usable in ordinary free play.

Verification: planned, not executed for this requirement.

## 4. Open questions

- **Blocking persistence decision:** how should current-schema data containing
  two workers on the same world square be handled? Recommended: reject with a
  useful error before exposing the model, without changing the file; never
  silently move a worker. Confirm this explicit scope during refinement.
- No new production multiplier is needed. Field ownership/occupation must be
  global even if the neighboring colony belongs to a different player; this
  does not add new diplomacy or land-purchase rules.
